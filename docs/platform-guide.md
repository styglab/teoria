# Teoria 사용 안내

Teoria는 데이터 자산과 업무 의미를 연결하고, AI 변경안을 검토하며, 업무 앱에서 활용하는 플랫폼이다.
현재 첫 업무 앱은 **FormatID — 규격서 기반 물품 구조화·분석**이다. 구현 범위와 다음 작업은 [로드맵](roadmap.md)을 따른다.

## 시작하기

1. [환경 설정](deployment/configuration.md)에 따라 인증정보를 준비한다.
2. [Compose](deployment/compose.md)에서 MLOps·Metadata/Ontology·FormatID 구성을 선택해 실행한다.
   MLOps는 모델 서빙을 포함하며 OpenMetadata·Semantic Runtime을 요구하지 않는다.
   MLflow는 Platform PostgreSQL의 전용 DB·계정을 사용하고 모델 파일은 객체 저장소에 둔다.
3. 기본 주소 `http://localhost:8081/`에서 관리자로 연결한다.

로컬 모듈별 실행과 대표 Flow의 확인 범위는 [Compose 검증 기록](verification/compose_modules_2026_10_30.md)을 참고한다.

EC2 배포는 [K3s 안내](deployment/k3s.md)를 따른다. 화면 경로·권한과 프런트엔드 개발 정보는
[관리 화면 참조](platform/admin_ui.md), 시스템별 책임은 [아키텍처](architecture/overview.md)에 있다.

## 어떤 화면에서 무엇을 하나

| 메뉴 | 작업 |
|---|---|
| 홈 | 검토 대기·실패한 실행·최근 작업 확인 |
| 데이터 자산 | 테이블·컬럼·설명·계보를 확인하고 진단 요청 |
| 의미 모델 | 온톨로지 작성·게시, 자산·용어와 의미 연결 |
| 검토함 | AI 제안·의미 연결·Ontology 변경안 검토 |
| 파이프라인 | 수동 실행·스케줄·취소 요청·이력 확인 |
| 모델 운영 | 선택 기능: 모델 버전·평가·추론 서비스 관리 |
| 앱 → FormatID | 문서 입력·분석 요청·규격서별 엔티티·관계·속성·원문 근거 탐색 |
| 연결 및 설정·개발 도구 | 관리자 인증·외부 연결·Runtime 개발 기능 |

홈과 검토함의 건수는 화면에서 조회한 범위다. 전체 누적 건수나 개인 할당 작업 수를 뜻하지 않는다.

## 데이터 자산을 정비하려면

1. 데이터 자산에서 테이블을 선택해 현재 설명·스키마·계보를 확인한다.
2. **진단 요청 → 자산 진단**에서 항목과 컬럼을 골라 실행한다. 진단은 Codex 기반 Worker가 수행한다.
3. 검토함에서 현재 값·제안·근거를 대조한다.
4. 권한 있는 사용자가 승인하면 적용 서비스가 원천 버전을 다시 확인하고 반영한다.

데이터 자산·설명·용어·거버넌스 정보의 기준은 OpenMetadata다. 진단 제출 자체가 원천을 변경하지 않는다.
자산 검색·정렬·누락 필터와 건수는 OpenMetadata 검색 색인에서 조회하며 화면에는 선택한 페이지만 가져온다.
관리자 인증이 필요한 경우 공통 관리자 연결을 사용하고, 인증 만료 후에는 다시 연결한다.
[진단 항목·법령 근거·실행 설정](platform/metadata/asset_assessment.md) ·
[제안의 검토·적용·복구](platform/metadata/suggestions.md)를 참고한다.

## 규격서를 처리하려면

1. **앱 → FormatID**에서 분류코드별 규격서를 검색한다. 새 문서는 **규격서 등록**에서 처리 방식을 선택한다.
2. 규격서 구조화 추출은 엔티티·관계·속성을 추출하고, 고정 표준 적용은 지정한 표준·프로파일로 결과를 정규화한다.
3. 실행 상태와 로그는 파이프라인에서 확인한다.
4. 파일명·공고번호·최근 처리 상태·처리 기간으로 목록을 좁힌다. 같은 원문·분류·공고의 재처리는 묶고, 최근 실패 시 이전 정상 결과를 제공한다. 파일 내용이 다른 버전은 별도 항목이다.
5. 문서를 열고 구성 트리에서 대상을 선택한다. 확인된 구성 관계가 없으면 목록을 제공한다. 물품·구성·작업·문서 등은 유형 필터로 좁힌다.
   핵심 명칭과 원문 이름·다른 표현을 함께 확인하고 별칭으로도 검색할 수 있다. 포장 계층은 별도로 선택한다. 상세는 기본 2열이며 근거를 열 때 원문 패널이 나타난다. 속성 행이나 대상별 원문 요구조건을 눌러
   근거를 비교하고, 연결 관계의 대상 버튼으로 이동한다. 납품·보증·일반 준수사항은 접힌 기타 요구사항에서 원문과 근거를 확인한다. 설치·제출 요구는 이행 완료와 구별한다.

| 보기 | 의미 |
|---|---|
| 추출 결과 (기본) | 해당 실행이 산출한 이름·구성 관계·값·단위·조건과 원문 근거 |
| 표준 매핑 | 프로파일 표준 적용·추출용 표준 초안·원문 결과를 구분. 표준 식별자·연결 또는 미매핑 상태 표시 |
| 규격서 비교 | 같은 분류의 결과 2–4개 선택. 표준 스냅샷·대상 개념·속성·역할·범위·단위가 같은 값만 같은 행에 표시; 각 셀에서 원문 확인 |
| 미분류·보류 항목 | 구성·귀속·의미를 확정하지 못한 항목. 삭제하거나 임의로 확정하지 않음 |

**규격서 결과**는 해당 실행의 최종 엔티티·관계·속성을 보여주는 읽기 화면이다.
문서를 선택하면 엔티티 목록과 구성·포장 구조, 선택 엔티티의 속성·관계, 원문 근거를 나란히 탐색한다.
처음에는 물품·구성품을 표시한다. 기존 장비·설치 지원·작업·문서는 접힌 관련 대상 영역이나 전체·유형 필터로 확인한다.
속성표는 원문 발췌를 함께 보여주며, 행 또는 **원문 보기**를 누르면 연결된 근거들을 한 패널에 표시한다.
정확한 원문 범위가 있으면 강조하고 **앞뒤 원문 함께 보기**로 문맥을 확인한다. 표시하는 것은 파싱한
문서 텍스트이며 스캔 문서는 OCR 텍스트임을 표시한다. 원본 PDF·오피스 파일의 시각적 미리보기는 아니다.
별도 속성명이 없는 `quantity`는 **수량**으로 표시한다. 일부 일반 분류의 표시명을 제공하되
이를 원문 속성명이나 표준 의미로 확정하지 않는다. 새 추출의 해석한 표시명은 근거 패널에서
**AI가 해석한 추출명**으로 구분한다. 표시명도 없으면 **속성명 확인 필요**로 남기고 필터로 모은다.
개요·용도 설명은 속성과 분리한 접힌 **물품 설명**에서 원문을 확인한다. 대상이 불명확한 설명은
**문서 설명 · 대상 미지정**에 보존한다. 성능·재질·보관 등의 실제 조건은 속성/요구조건에 남긴다.
새 Worker와 원문 대조를 거친 샘플 10개 결과를 미분류 목록에 반영했다. 보류 항목은 그대로 표시한다.
이전 실행 결과를 소급 변경하지 않으므로 최근 처리 시각·선택한 실행과 원문을 함께 확인한다.
2026-11-02 개발판에는 구매 행·수량과 구성관계의 분리 및 기준 목록 판독 상태·제한된 PDF 영역 복구를 추가했다.
이 추가 변경은 Worker·웹에 배포했고 샘플 10개의 새 결과를 반영했다.
초음파 스캔 PDF는 파서 동시 실행을 제한한 뒤 재처리했다. 최근 처리 시각과 실행별 결과를 확인한다.
내부 식별자와 원문 참조 ID는 근거 패널의 접힌 **추출 정보**에서 확인한다.
추출 화면에는 표준 미매핑 표시를 반복하지 않으며, **표준 매핑**에서 별도로 확인한다.
원문에 통합 물품의 구성 목록이 있으면 해당 물품과 직접 구성 순서를 유지한다.
해석된 하위 구성 연결은 부모 아래 '구성 관계 검토 중'으로 표시하고, 부모 연결이 없거나 보류됐다는 이유로
하위 대상을 새 최상위 물품으로 올리지 않는다. 연결되지 않은 대상도 별도 목록에서 확인할 수 있다.
설치·교육·보증·제출 조건과 원문 근거는 보존하며, 이를 구매 물품의 물리 구성품으로 표시하지 않는다.
관계는 출발·도착 대상과 방향을 표시하고 선택 엔티티 또는 규격서 전체 범위로 볼 수 있다.
미해결 항목에는 대상 연결·근거 누락 속성, 보류 관계, 추출 범위·의미·범위 미확정 기록을 모은다.
통신·호환·의존·지원·작업·문서의 보류 관계는 접힌 '부가 관계 검토'로 분리하며 핵심 미해결 개수에 합산하지 않는다.
새 추출에서는 이러한 부가 관계 보류만으로 물품 구성·속성 추출을 부분 완료로 표시하지 않는다. 과거 실행의 상태는 유지한다.
문서별 결과 행에서 해당 문서로 이동하며 `document` URL 값으로 선택을 복원한다.
실패·제외 문서도 선택 목록에 남겨 구조화 결과가 없는 원인을 구분한다.
FormatID에서 프로파일 검토·승인을 수행하지 않으며, Ontology·프로파일 작성·승인은 별도 의미 관리 책임이다.

트리·속성·원문은 각각 스크롤할 수 있다. 모바일에서는 목록·상세·근거 패널을 전환한다.
`partial`은 보류·미해결 항목이 남았다는 뜻이며 Prefect의 `Completed`와 의미 정확도는 다르다.
파이프라인은 이미지 PDF에 Kory OCR을 사용하고 실제 사용 페이지와 원문 위치를 기록한다.
독립 구매 행의 속성 귀속과 속성별 원문 근거를 검사하며, 누락 대상의 제한된 복구는
부모 관계·납품 수량의 자동 확정을 뜻하지 않는다. 읽지 못한 OCR 페이지는 부분 완료로 남는다.

사전 관리에서는 검증된 변경 묶음의 자동 반영을 설정할 수 있다. 평가 문서가 부족하거나 근거·품질 검사를
통과하지 못하면 보류한다. 사전의 반영이 Published Ontology 게시를 뜻하지는 않는다.
분류·목표 파일 수·평가 분리·자동 반영·Codex 단계·재실행 방법은
[규격서 파이프라인](procurement_specification_processing/pipeline.md)을 따른다.

## 결과는 어디에 저장되나

규격서 원본·추출·보고서는 MinIO/S3에, 실행 상태·산출물 참조는 Data DB에 저장한다.
Ontology·사전·변경 제안·승인 이력은 Application DB가 관리한다.
[저장소 책임](architecture/overview.md#누가-무엇을-저장하나) · [DB 운영](pipelines/database.md)을 참고한다.


모바일 FormatID 목록은 카드로 제공하며 **검색·필터**를 펼쳐 조회 조건을 바꾼다.
목록에서 문서를 열고 돌아오면 이전 위치와 비교 선택을 복원한다. 갱신 중에는 기존 행을
유지하며, 조건이 다른 이전 결과를 보고 있으면 이를 표시한다. 분류와 문서 조회 오류는
각 영역에서 다시 조회할 수 있다. 표준 적용 결과에서는 요구값·단위·조건을 우선 확인하고
**원문 값·단위**, **표준 식별자**를 펼쳐 세부 기록을 확인한다.
