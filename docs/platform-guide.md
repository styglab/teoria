# Teoria 사용 안내

Teoria는 데이터 자산과 업무 의미를 연결하고, AI 변경안을 검토하며, 업무 앱에서 활용하는 플랫폼이다.
현재 첫 업무 앱은 **FormatID — 규격서 기반 물품 구조화·분석**이다. 구현 범위와 다음 작업은 [로드맵](roadmap.md)을 따른다.

Data는 원본·문서별 관찰·근거를, Ontology는 소스에 독립적인 업무 정의를 관리한다.
물품 사전은 표현 연결, 프로파일은 적용 규칙을 관리하며 별도 업무 정의를 만들지 않는다.
게시 정의는 사전 등록 없이 인증된 Ontology publication API로 조회할 수 있다.
규격서의 선택형 개념 연결 비교는 검토 제안이며 승인·게시·실제 물품 Runtime 제공과 구분한다.
계층과 저장 권위는 [아키텍처](architecture/overview.md)를 따른다.
물품의 현재 작성안은 goods 2.0.0 Draft다. 서버·메모리 모듈의 업무 정의와 문서별 요구·근거를
구분하며, 예전 사전 정의 객체를 새 의미 원장으로 사용하지 않는다. [물품 모델](architecture/specification_goods_model.md)과
[프로파일 예시](procurement_specification_processing/normalization_profiles.md)를 검토한 뒤 실제 게시 절차를 진행한다.
기존 1.0.0을 보존한 실제 DB의 새 Draft 준비와 규격서 대조 결과는
[11월 9일 검증 기록](verification/goods_native_draft_preparation_2026_11_09.md)을 따른다.

## 시작하기

1. [환경 설정](deployment/configuration.md)에 따라 인증정보를 준비한다.
2. [Compose](deployment/compose.md)에서 MLOps·Metadata/Ontology·FormatID 구성을 선택해 실행한다.
   MLOps는 모델 서빙을 포함하며 OpenMetadata·Semantic Runtime을 요구하지 않는다.
   MLflow는 Platform PostgreSQL의 전용 DB·계정을 사용하고 모델 파일은 객체 저장소에 둔다.
3. 기본 주소 `http://localhost:8081/`에서 관리자로 연결한다.

로컬 모듈별 실행과 대표 Flow의 확인 범위는 [Compose 검증 기록](verification/compose_modules_2026_10_30.md)을 참고한다.

EC2 배포는 [K3s 안내](deployment/k3s.md)를 따른다. 화면 경로·권한과 프런트엔드 개발 정보는
[관리 화면 참조](platform/admin_ui.md), 시스템별 책임은 [아키텍처](architecture/overview.md)에 있다.

## 작업 공간 선택

홈과 왼쪽 메뉴는 **Ontology·업무 실행**과 **모델 개발·운영**으로 나뉜다.
배포에서 활성화한 기능만 표시하며 모델 작업 공간은 관리자 연결 후 사용 가능 여부를 확인한다.
두 영역은 독립적으로 사용할 수 있다. **공통 운영**의 파이프라인과 연결·설정은 함께 사용하고,
**업무 앱**에서 FormatID를 연다. 모델 평가·등록·추론 서비스의 현재 범위는 고정 데모 중심이다.
모델을 Capability에 연결하는 업무 기능은 아직 제공하지 않는다.

홈과 검토함의 건수는 화면에서 조회한 범위다. 전체 누적 건수나 개인 할당 작업 수를 뜻하지 않는다.

## 데이터 자산을 정비하려면

1. 데이터 자산에서 테이블을 선택해 현재 설명·스키마·계보를 확인한다.
2. **진단 요청 → 자산 진단**에서 항목과 컬럼을 골라 실행한다. 진단은 Codex 기반 Worker가 수행한다.
3. 검토함에서 현재 값·제안·근거를 대조한다.
4. 권한 있는 사용자가 승인하면 적용 서비스가 원천 버전을 다시 확인하고 반영한다.

데이터 자산·설명·용어·거버넌스 정보의 기준은 OpenMetadata다. 진단 제출 자체가 원천을 변경하지 않는다.
자산 검색·정렬·누락 필터와 건수는 OpenMetadata 검색 색인에서 조회하며 화면에는 선택한 페이지만 가져온다.
관리자 인증이 필요한 경우 공통 관리자 연결을 사용하고, 인증 만료 후에는 다시 연결한다.
[진단 항목·법령 근거·실행 설정](platform/metadata/asset_assessment.md) ·
[제안의 검토·적용·복구](platform/metadata/suggestions.md)를 참고한다.

## 규격서를 처리하려면

1. **업무 앱 → FormatID**에서 분류코드별 규격서를 검색한다. 새 문서는 **규격서 등록**에서 처리 방식을 선택한다.
2. 규격서 구조화 추출은 엔티티·관계·속성을 추출하고, 고정 표준 적용은 승인된 적용 버전을 선택해 당시 표준·프로파일과 사전으로 결과를 정규화한다.
3. 실행 상태와 로그는 파이프라인에서 확인한다.
4. 파일명·공고번호·최근 처리 상태·처리 기간으로 목록을 좁힌다. 같은 원문·분류·공고의 재처리는 묶고, 최근 실패 시 이전 정상 결과를 제공한다. 파일 내용이 다른 버전은 별도 항목이다.
5. 문서를 열고 구성 트리에서 대상을 선택한다. 확인된 구성 관계가 없으면 목록을 제공한다. 물품·구성·작업·문서 등은 유형 필터로 좁힌다.
   핵심 명칭과 원문 이름·다른 표현을 함께 확인하고 별칭으로도 검색할 수 있다. 포장 계층은 별도로 선택한다. 상세는 기본 2열이며 근거를 열 때 원문 패널이 나타난다. 속성 행이나 대상별 원문 요구조건을 눌러
   근거를 비교하고, 연결 관계의 대상 버튼으로 이동한다. 납품·보증·일반 준수사항은 접힌 기타 요구사항에서 원문과 근거를 확인한다. 설치·제출 요구는 이행 완료와 구별한다.

| 보기 | 의미 |
|---|---|
| 추출 결과 (기본) | 해당 실행이 산출한 이름·구성 관계·값·단위·조건과 원문 근거 |
| 표준 매핑 | 프로파일 표준 적용·추출용 표준 초안·원문 결과를 구분. 표준 식별자·연결 또는 미매핑 상태 표시 |
| 규격서 비교 | 같은 분류의 결과 2–4개 선택. 표준 스냅샷·대상 개념·속성·역할·범위·단위가 같은 값만 같은 행에 표시; 각 셀에서 원문 확인 |
| 미분류·보류 항목 | 구성·귀속·의미를 확정하지 못한 항목. 삭제하거나 임의로 확정하지 않음 |

**규격서 결과**는 해당 실행의 최종 엔티티·관계·속성을 보여주는 읽기 화면이다.
문서를 선택하면 엔티티 목록과 구성·포장 구조, 선택 엔티티의 속성·관계, 원문 근거를 나란히 탐색한다.
처음에는 물품·구성품을 표시한다. 기존 장비·설치 지원·작업·문서는 접힌 관련 대상 영역이나 전체·유형 필터로 확인한다.
속성표는 원문 발췌를 함께 보여주며, 행 또는 **원문 보기**를 누르면 연결된 근거들을 한 패널에 표시한다.
정확한 원문 범위가 있으면 강조하고 **앞뒤 원문 함께 보기**로 문맥을 확인한다. 표시하는 것은 파싱한
문서 텍스트이며 스캔 문서는 OCR 텍스트임을 표시한다. 원본 PDF·오피스 파일의 시각적 미리보기는 아니다.
별도 속성명이 없는 `quantity`는 **수량**으로 표시한다. 일부 일반 분류의 표시명을 제공하되
이를 원문 속성명이나 표준 의미로 확정하지 않는다. 새 추출의 해석한 표시명은 근거 패널에서
**AI가 해석한 추출명**으로 구분한다. 표시명도 없으면 **속성명 확인 필요**로 남기고 필터로 모은다.
개요·용도 설명은 속성과 분리한 접힌 **물품 설명**에서 원문을 확인한다. 대상이 불명확한 설명은
**문서 설명 · 대상 미지정**에 보존한다. 성능·재질·보관 등의 실제 조건은 속성/요구조건에 남긴다.
새 Worker와 원문 대조를 거친 샘플 10개 결과를 미분류 목록에 반영했다. 보류 항목은 그대로 표시한다.
이전 실행 결과를 소급 변경하지 않으므로 최근 처리 시각·선택한 실행과 원문을 함께 확인한다.
2026-11-02 개발판에는 구매 행·수량과 구성관계의 분리 및 기준 목록 판독 상태·제한된 PDF 영역 복구를 추가했다.
이 추가 변경은 Worker·웹에 배포했고 샘플 10개의 새 결과를 반영했다.
초음파 스캔 PDF는 파서 동시 실행을 제한한 뒤 재처리했다. 최근 처리 시각과 실행별 결과를 확인한다.
내부 식별자와 원문 참조 ID는 근거 패널의 접힌 **추출 정보**에서 확인한다.
추출 화면에는 표준 미매핑 표시를 반복하지 않으며, **표준 매핑**에서 별도로 확인한다.
구성 탐색은 실제 구매 물품부터 시작한다. 단일 서버 구매는 서버, 증설 부품 구매는 해당 부품,
여러 독립 물품은 각각 루트로 표시한다. 구매 범위명은 별도 공통 규격 영역에서 확인한다.
원문에 통합 물품의 구성 목록이 있으면 해당 물품과 직접 구성 순서를 유지한다.
파이프라인은 최상위 구매 물품 포함 3계층을 기본 구성으로 분류한다. 4계층 이하는 접힌
**세부 구성**에서 원래 부모·속성·원문을 확인하며, 기본 깊이에 맞추려고 관계를 바꾸지 않는다.
3계층 대상에서는 더 깊은 세부 구성의 속성도 기본으로 함께 표시한다. 속성 표의 **대상**은
CPU·RAM처럼 실제 소유 대상을 유지한다. **속성 범위 → 이 대상만**을 선택하면 직접 속성만 본다.
누락된 수치 단위는 원문 숫자의 정확한 위치 바로 뒤에 명시돼 있을 때만 보완한다.
원문 단위와 문자 위치 근거를 보존하며 대상명으로 단위를 추정하지 않는다.
값을 표시할 때 `이상·이하·초과·미만`은 값·단위 뒤에 둔다(예: `5 EA 이상`).
원문 보기와 저장된 값·단위·조건은 그대로 유지한다.
수치의 근거는 숫자 전체를 가리켜야 한다. 예를 들어 `48MB`의 일부인 `8`을 코어 수의
근거로 표시하지 않으며, 잘못된 값 위치는 추출 및 결과 재사용 검증에서 거부한다.
해석된 하위 구성 연결은 부모 아래 '구성 관계 검토 중'으로 표시하고, 부모 연결이 없거나 보류됐다는 이유로
하위 대상을 새 최상위 물품으로 올리지 않는다. 연결되지 않은 대상은 상위 물품·구매 범위 확인 필요 영역에서 확인할 수 있다.
설치·교육·보증·제출 조건과 원문 근거는 보존하며, 이를 구매 물품의 물리 구성품으로 표시하지 않는다.
관계는 출발·도착 대상과 방향을 표시하고 선택 엔티티 또는 규격서 전체 범위로 볼 수 있다.
미해결 항목에는 대상 연결·근거 누락 속성, 보류 관계, 추출 범위·의미·범위 미확정 기록을 모은다.
통신·호환·의존·지원·작업·문서의 보류 관계는 접힌 '부가 관계 검토'로 분리하며 핵심 미해결 개수에 합산하지 않는다.
새 추출에서는 이러한 부가 관계 보류만으로 물품 구성·속성 추출을 부분 완료로 표시하지 않는다. 과거 실행의 상태는 유지한다.
문서별 결과 행에서 해당 문서로 이동하며 `document` URL 값으로 선택을 복원한다.
실패·제외 문서도 선택 목록에 남겨 구조화 결과가 없는 원인을 구분한다.
FormatID에서 프로파일 검토·승인을 수행하지 않으며, Ontology·프로파일 작성·승인은 별도 의미 관리 책임이다.

트리·속성·원문은 각각 스크롤할 수 있다. 모바일에서는 목록·상세·근거 패널을 전환한다.
`partial`은 보류·미해결 항목이 남았다는 뜻이며 Prefect의 `Completed`와 의미 정확도는 다르다.
파이프라인은 이미지 PDF에 Kory OCR을 사용하고 실제 사용 페이지와 원문 위치를 기록한다.
독립 구매 행의 속성 귀속과 속성별 원문 근거를 검사하며, 누락 대상의 제한된 복구는
부모 관계·납품 수량의 자동 확정을 뜻하지 않는다. 읽지 못한 OCR 페이지는 부분 완료로 남는다.

표준관리는 게시된 Ontology와 승인된 원문 표현 연결을 고정해 사용합니다. 미해결 표현은
원문 근거를 포함한 검토 후보로 남기며 새 로컬 사전 의미를 자동 승인하지 않습니다.
Ontology가 없어도 추출·원문 보존은 계속합니다. 분류·평가 분리·재실행은
[규격서 파이프라인](procurement_specification_processing/pipeline.md)을 따릅니다.

선택적으로 게시 개념을 참고하는 의미 연결 비교를 실행할 수 있습니다. 결과의
**Ontology 의미 연결 비교**에서 참고한 게시 버전과 기존 승인 연결·새 제안·원문을 함께 봅니다.
원문 관찰과 프로파일 적용 결과는 유지하며, 미연결 항목도 문맥 확대·Ontology 검토 후보로
보존합니다. 새 제안은 승인된 의미가 아닙니다. 현재 입력 방법과 검증 범위는
[연결 비교 안내](procurement_specification_processing/pipeline.md#고정-관찰의-ontology-연결-비교)를 따릅니다.

추출의 소유 대상·scope를 다시 해석해야 하면
[해석 제안 CLI](procurement_specification_processing/normalization_profiles.md#소유-대상범위의-해석-제안)로
원문과 제안·근거를 분리해 저장할 수 있습니다. Draft를 참고할 수 있으나 검토 대기 산출물이며
FormatID의 승인 UI나 프로파일 적용으로 연결되지는 않습니다.

## 사전을 검토하고 적용 기준을 고정하려면

1. **도메인 관리 → 물품 사전**에서 품목코드를 선택하고 물품·구성 유형, 속성 정의, 원문 표현, 원문 표현 연결과 검토 대기를 조회한다. 품목이 없는 과거 관찰은 **품목 미확인**에서 확인한다. 정의는 **온톨로지**에서 작성·검토·게시하고 사전에서는 게시된 개념을 조회한다.
2. 원문 근거, 적용 물품 유형, 자료형·단위와 관련 문서를 확인한다. 원문 표현과 게시된 개념의 연결을 제안하고 사유를 입력해 승인·반려·사용 중단한다. 과거 정의는 이력에서 Ontology Draft로 가져올 수 있다. `ontology_owner` 권한이 필요하다.
3. **FormatID → 처리 기준**에서 완료 또는 부분 완료된 표준관리 실행을 선택해 결과를 검토한다. 이름과 승인 근거를 입력하면 해당 표준과 승인된 사전의 불변 스냅샷을 함께 보관한다. 이 묶음은 규격서 처리 기준이며 플랫폼 공통 의미 버전이 아니다.
4. FormatID의 **고정 표준 적용**에서 승인된 버전을 선택한다. 이 경로는 사전을 자동 변경하지 않으며 버전의 분류·참조·checksum을 서버에서 검증한다.

사전은 물품 도메인의 선택 도구다. 모든 Ontology에 사전이 필요한 것은 아니며, 추출용 표준 초안을 고정해도 Published Ontology가 되지는 않는다.

Ontology의 업무 개념을 펼치면 연결된 데이터·용어와 승인 상태를 확인할 수 있다. **데이터·용어 연결**에서 선택 개념 또는 모델 범위로 연결을 조회·제안·검토한다. 물품 사전의 원문 표현 연결과는 별도 기능이다.

## 사전·프로파일·Ontology는 어떻게 다른가

| 구분 | 역할 |
|---|---|
| 원문 표현 사전 | 문서의 명칭·소유 대상·근거 보존 |
| 표현·개념 연결 | 원문 표현과 게시된 Ontology Stable Concept ID의 연결·승인 이력 |
| 정규화 프로파일 | 게시된 Ontology 개념을 문서에 적용하는 승인된 규칙 |
| Business Ontology | 여러 시스템에서 유지할 업무 개념·속성·관계 정의 |

[사전](platform/goods_dictionary.md) · [프로파일](procurement_specification_processing/normalization_profiles.md) ·
[Ontology](platform/ontology.md)에서 각 작성·승인 경계를 확인한다.

## 결과는 어디에 저장되나

규격서 원본·추출·보고서는 MinIO/S3에, 실행 상태·산출물 참조는 Data DB에 저장한다.
Ontology·사전·변경 제안·승인 이력은 Application DB가 관리한다.
[저장소 책임](architecture/overview.md#누가-무엇을-저장하나) · [DB 운영](pipelines/database.md)을 참고한다.


모바일 FormatID 목록은 카드로 제공하며 **검색·필터**를 펼쳐 조회 조건을 바꾼다.
목록에서 문서를 열고 돌아오면 이전 위치와 비교 선택을 복원한다. 갱신 중에는 기존 행을
유지하며, 조건이 다른 이전 결과를 보고 있으면 이를 표시한다. 분류와 문서 조회 오류는
각 영역에서 다시 조회할 수 있다. 표준 적용 결과에서는 요구값·단위·조건을 우선 확인하고
**원문 값·단위**, **표준 식별자**를 펼쳐 세부 기록을 확인한다.

규격서의 반복 개선은 기존 `improve-specification-processing` 스킬과 평가 CLI로 수행한다.
새 원본의 개발/검증 분할과 기존 샘플 회귀를 분리하고, 사이클 종료 시 최종·중간 평가 산출물은
삭제한다. 입력 원본·최소 사례·변경 코드·비교 요약과 사용 이력은 유지한다.
[평가 운영](procurement_specification_processing/evaluation.md)의 원본 탐색·종료·전체 통합 검증 기준을 따른다.

온톨로지의 **버전 검토**에서는 문서 프로파일·사전 표현 연결·API Mapping의 변경 영향과
재검토 대상을 함께 확인한다. 문서/API의 같은 개념·단위 참조와 정보 성격 구분은
[Mapping 안내](platform/registry/mappings.md)를 따른다. 현재 메모리 용량 대조는 합성 사례로
검증한 코드 범위이며 운영 API 연결·배포나 전체 물품 적합성 검증 완료가 아니다.

## 규격서 검토에서 재처리까지

새 분석 화면에서는 `ontology_owner` 권한이 있으면 **원문 표현과 추출 기준을 자동 승인·적용**이
기본으로 켜진다. 근거가 검증되고 대상·역할·범위가 확인된 값은 `source_literal` 추출 규칙으로
채택해 같은 실행에 적용한다. 값·단위·연산자·조건을 원문 그대로 보존하고 수치 비교는 허용하지
않는다. Business Ontology 정의·게시와 표현의 개념 동등 연결 승인은 별도다.

처리가 끝나면 실제 적용 규칙이 있는 표준과 사용한 사전 버전을 인증된 Admin API로 자동
승인·고정하고, 실행 결과에 처리 기준 ID와 승인 주체를 기록한다. 같은 요청을 재시도해도 같은
버전을 재사용한다. 적용 규칙 0개 또는 처리 뒤 사전 의미가 변경된 경우는 보류한다.
기존 고정 표준 적용 모드는 버전을 변경하지 않는다. 자동 적용을 끄면 기존 검토 경로를 사용한다.

현재 Compose에는 자동 승인·적용과 완전한 숫자 근거 검사 보강이 반영됐다.
실제 화면·Worker 확인과 전체 문서 품질 평가의 남은 범위는
[배포·평가 기록](verification/specification_workflow_validation_2026_11_08.md)을 따른다.

FormatID 실행 결과의 **검토와 다음 작업**에서 원문 표현·의미 연결 검토와 처리 기준 승인으로
이동한다. 승인 화면은 원본 실행을 선택한 상태로 열 수 있으며, 선택한 실행이 첫 페이지 밖에
있어도 직접 조회한다. 승인된 처리 기준에서 **이 기준으로 원본 문서 재처리**를 선택하면
등록된 원본 URI·확인된 해시와 승인된 표준·사전 참조를 사용해 새 실행을 요청한다.
기존 결과는 유지한다. 실행 중인 작업과 원본 참조가 불완전한 과거 이력은 재처리 입력으로
사용하지 않는다. 다시 업로드할 필요 없이 처리 기준을 변경할 수 있다.

승인 화면은 선택한 실행의 실제 정의·적용 규칙 수를 확인한다. 적용 규칙이 없는 빈 표준은
승인하지 않으며 작성·검토가 필요한 이유를 표시한다. 과거에 승인된 빈 기준도 새 실행에는
사용할 수 없다. CLI·Worker는 처리 기준 ID를 사용할 때 인증된 Admin API의 승인 상태와
고정 참조·분류·checksum·규칙을 실행 상태 등록 전에 확인한다.

실행 목록은 최근 7일의 실행 실패·부분 완료·처리 중과 문서별 실패·부분 추출을 표시한다.
새 실행에는 원문 검증 오류·격리 속성·문서 실패 비율을 표시하고 처리 코드·모델별로 집계한다.
과거 미측정 실행은 측정값이 없는 것으로 표시한다. 원문 검증 한도를 넘으면 처리 기준의
자동 승인을 보류한다. 격리된 속성은 원문과 거절 사유를 확인하고 모델 호출 없이 검증을
재현할 수 있다. 실행 결과의 **실패·검증 보류 문서만 다시 추출**로 해당 원본만 새 실행한다.
이 수치는 실행 상태이며 의미 정확도나 독립 평가 점수가 아니다.
고정 평가 사례가 미일치해도 곧바로 원문 값이 누락됐다고 판단하지 않는다. 원문에서 확인한
대상 명칭·상하위 대상과 최소 인용 범위가 평가 기준과 다른지 결과 화면에서 함께 확인한다.
평가 기준 보정과 추출기 수정의 효과는 별도로 기록한다.
새 실행의 산출물에는 `execution_receipt.json`이 포함된다. 코드 revision, 원본 해시, 파서 버전,
요청 모델명, 고정 처리 기준·표준·사전·Ontology 참조와 산출물 checksum을 기록한다.
모델명의 불변 버전 확인과 독립 평가 연결은 아직 없으므로 각각 미검증·미연결로 표시한다.
본문·원문·관찰은 객체 저장소에 유지하고 DB에는 실행 상태와 참조를 저장한다.
새 공개 원본의 실제 처리·승인·재처리 범위와 남은 의미 승인은
[2026-11-08 검증 기록](verification/specification_workflow_validation_2026_11_08.md)을 참고한다.
