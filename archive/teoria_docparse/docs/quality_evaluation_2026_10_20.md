# 규격서 원문 기준 품질 평가 — kordoc 4.22.15 / Python 0.4.0

2026-10-20. `.artifacts/procurement_specifications/`에 있는 기존 규격서 10개를
원본 kordoc과 Python 패키지로 **새로 파싱**했다. Python은 기본 pdfplumber와
선택 MuPDF 경로를 모두 실행했다. 글자층이 없는 PDF와 글자·이미지가 섞인 PDF는
양쪽 모두 **OCR을 켜서 추가 실행**했다. 이번 작업에서 파서 구현은 변경하지 않았다.

**현재 Python이 원본보다 전체적으로 더 정확하지는 않다.** 독립 요구사항 양식의
분리는 Python이 더 잘하고, PDF 제목 계층·표 오탐 억제·글자층 없는 PDF의 OCR과
표 복원은 원본이 더 잘한다. 일반 규격값과 HWP/HWPX/DOCX의 검사한 셀은 동등했다.
혼합 PDF의 그림 속 핵심 규격은 OCR을 켜도 양쪽 모두 놓쳤다.

## 평가 기준

원본 kordoc 출력은 정답으로 사용하지 않았다.

- PDF 5개 **25쪽**의 원문 렌더링을 살펴보고, 규격값·행/열/병합·요구사항 ID·제목·
  표가 아닌 영역에 대한 **84개 진단 항목**을 만들었다. 본문 전체를 글자별로 전사한
  정답은 아니며, 항목 수를 문서 전체 정확도로 표현하지 않는다.
- HWP 2개는 원본 OLE의 BodyText 레코드에서 표 정의와 셀 주소·병합·본문을 직접 읽었다.
  HWPX 2개와 DOCX 1개는 원본 ZIP/XML을 읽었다. 삭제 이력은 제외하고 삽입된 현재
  본문은 포함한다. 결과는 **표 10개, 셀 221개**다. 파서 함수를 사용해 정답을 만들지 않았다.
- HWP의 외부 셀은 자기 문단을, 내부 표는 그 표의 셀을 각각 검사한다. 평탄화된 외부
  셀 텍스트에 내부 표가 포함됐다는 이유로 오류로 세지 않는다.
- 숫자·단위·대소문자·연산자는 보존한다. NFC, 공백과 Markdown/HTML 표시만 정규화한다.
  예를 들어 `3200W`와 `320ow`, `128GB`와 `128MB`는 다르다.
- 글자가 없어서 읽기 순서를 판단할 수 없는 항목은 `not_evaluable`로 남긴다.
  빈 출력이나 `success=true`를 품질 성공으로 세지 않는다.

각 항목의 문서 입력 SHA-256과 원문 근거는
[정답 항목](../verification/quality_labels_2026_10_20.json)에 고정했다.
현재 표본은 이전 개발에도 사용한 문서다. 단일 검토자의 진단이며 독립 holdout이나
전문가 이중 검수가 아니다. 전체 서식·의미·이미지·출처 정확도를 승인한 결과도 아니다.

### 독립 양식 분리: Python이 나은 부분

`doc_01`(GPU 카드 구매 규격서, 17쪽)의 6~17쪽에는 고유번호를 가진 독립 양식이
20개 있다. 5쪽 목록에는 `MAR-002`가 빠져 있지만, 실제 17쪽에는 존재한다.
원문 자체의 누락을 임의로 수정해 정답에 넣은 것이 아니라 실제 상세 양식을 확인했다.

원본은 `ECR-001/002`, `TER-001~004`, `SER-001/002`, `PMR-001/002`,
`PSR-001/002`, `PSR-003/004`, `MAR-001/002`를 각각 한 표로 합친다.
20개 양식이 11개 표로 묶이며, 그중 독립성을 유지한 양식은 4개다.
**16개 요구사항의 내용이 전부 사라졌다는 뜻은 아니다.** 고유번호가 다른 양식의
경계와 반복 항목명을 하나의 표로 접은 것이 문제다. Python은 20개를 별도로 유지한다.

### 제목과 오탐 표: Python이 뒤지는 부분

같은 문서의 파란 `개요`·`주요내용` 배너, 4쪽 표의 별도 중복 헤더,
11쪽 `SER-001` 본문 일부, 15쪽 `PSR-002` 본문 일부를 Python은 불필요한 표로 만든다.
해당 본문 문구는 부모 요구사항 안에 남아 있어, 이를 본문 누락으로 판정하지 않았다.
원본에도 `주요내용` 배너의 표 오탐 1개가 남지만 나머지 4곳은 피한다.

PDF 제목 7개 중 원본은 6개를 heading으로 표현한다. Python의 PDF 문단 생성은
글자를 줄로 묶은 뒤 paragraph로 출력하므로, 검사한 제목 7개 모두 계층을 잃는다.
본문 문자열이 같은 문서에서도 이 차이가 존재한다. 기존 48/68 일치율에는
이 제목·서식 차이가 반영되지 않았다.

### OCR: 실제 규격서에서 드러난 차이

`doc_09`는 사람이 읽을 수 있는 글자가 있지만 추출 가능한 글자층은 없는 PDF다.
OCR을 끄면 양쪽 모두 본문을 복원하지 못한다. OCR을 켜면 다음 차이가 난다.

- 양쪽 모두 `24 Core`, `128MB`, `3.2 GHz`, `1.92TB` 등 주요 수치를 읽는다.
- 원본은 12개 확인 항목 중 11개를 읽고, 품목·분류번호·단위·수량의 2×6 표도 복원한다.
- Python은 9개를 읽는다. GPU 컨테이너 런타임 문장과 대용량 메모리 설명 문구를
  놓치며, 표 헤더의 인식과 읽기 순서도 불안정하다. OCR 결과는 표 대신 문단으로 남는다.
- 원문의 전원 규격 `3200W`는 양쪽 모두 `320ow`로 잘못 읽었다. 숫자 정규화로
  자동 보정해 정답 처리하지 않았다. 해당 글자가 없는 전체 순서 검사는 판정 보류다.

`doc_10`은 3~4쪽의 핵심 규격이 많은 작은 이미지로 구성된 혼합 PDF다.
OCR을 켜도 `EPYC 9355`, `32C/64T`, `32GB 6400MHz ECC RDIMM`,
`1300W`, `2000W` 등을 포함한 13개 확인 항목을 **양쪽 모두 복원하지 못했다.**
원본에는 `OCR_APPLIED`가 있지만 실제 핵심 내용은 빠져 있다. Python은 글자층이
조금이라도 있는 쪽을 전체 OCR 대상으로 보내지 않는 구현이라 이 경로의 누락이 남는다.

이 비교는 각 패키지의 실제 OCR 구현을 사용했다. 원본은 기본 PP-OCRv5 mobile
검출기/한국어 인식기, Python은 설치된 RapidOCR 기본 PP-OCRv6 검출기와 PP-OCRv5
한국어 인식기를 사용했다. 전처리·해상도·검출 모델까지 같은 조건으로 통제한 OCR
모델 자체의 비교는 아니다. 모델 파일과 의존성 버전/hash를 별도로 기록했다.

## 개선 우선순위

1. **혼합 PDF의 누락 영역 OCR**: `page.chars` 존재만으로 OCR을 생략하지 않고,
   이미지/윤곽선 영역의 실제 미복원 규격을 검출하고 좌표에 맞게 기존 본문과 합쳐야 한다.
2. **OCR 좌표의 표 복원**: 인식 문단만 붙이지 않고 원문의 괘선·셀에 배치해야 한다.
   `doc_09`의 품목/단위/수량 표가 직접적인 회귀 기준이다.
3. **제목 계층과 장식 구별**: 글꼴 크기·굵기·공백을 이용해 제목을 복원하고,
   장식 배너와 중복 헤더·본문 클리핑을 표로 인식하지 않도록 보완해야 한다.
4. **숫자·단위 인식 검증**: `3200W` 같은 실제 오인식을 먼저 측정한다.
   `2-core/64-thread`, `Nvidia 100` 등 원문에 있는 오타는 임의 교정하지 않는다.

기존 원문 경로가 있는 환경에서 결과를 다시 평가하는 명령이다.

```bash
archive/teoria_docparse/.venv/bin/python \
  archive/teoria_docparse/verification/quality_review.py \
  --manifest .artifacts/procurement_specifications/parser_evaluation_2026_10_20/sample_manifest.json \
  --labels archive/teoria_docparse/verification/quality_labels_2026_10_20.json \
  --runs archive/teoria_docparse/.artifacts/quality_review_2026_10_20 \
  --ocr archive/teoria_docparse/.artifacts/quality_review_2026_10_20/ocr \
  --output archive/teoria_docparse/verification/results/quality_review_10_v0_4_0.json
```

새 파싱은 `teoria-docparse-compare`에 같은 manifest와 원본 패키지/bridge 경로를 주고
`--pdf-backend pdfplumber` / `pymupdf`를 각각 지정한다. 이전 증거를 보존하도록
각 실행의 `--output`은 새 디렉터리를 사용한다. OCR 원본 실행 config는 해당 실행의
`ocr/run_config.json`에 보존했고, Python에는 동일 문서에 `ParseOptions(ocr=True)`를
적용했다. 이번 결과는 활성 Pipeline·Prefect·배포와 연결하지 않았다.
