# PDF 이미지 셀 표 복원 — 2026-10-26

**사용자가 두 검증 조건의 예외를 명시적으로 허용해, 검증한 후보를 현재 파서에 적용했다.**
PyMuPDF와 의존성·잠금 파일은 그대로 유지했다. 수용 gate의 정책·정답·기존 테스트를
수정하지 않았으며, 원래 gate의 미채택 판정도 보존했다.

## 원문에서 확인한 결함

기존 엔진 실험의 개발 문서 `r26bk01723086_000_02` 첫 페이지에는 하나의 7행×4열
표가 있다. 셀의 글자는 이미지로 저장돼 있고 선 격자는 현재 엔진이 이미 감지한다.
그러나 `pdf.py`는 `has_text()`가 거짓인 표를 버려 격자는 사라지고 이미지 31개만
페이지 블록에 남긴다. 이 문서에 출력되는 2행×4열과 3행×4열 표는 각각 2쪽과 4쪽의
다른 표다. 첫 페이지 표가 그 두 조각으로 나뉜다는 종전 설명은 잘못이었다.
기존 첫 페이지 7행×4열 원문 정답은 변경하지 않았다.

고정 회귀 실행에서 같은 원인의 출력 변화가 `corpus_040`에 발견됐다. 원문 2쪽의
구매품목 표는 2행×4열이며 글자가 이미지다. 원문 렌더를 확인해 이 변화도 실제 표의
복원임을 확인했다. 회귀 결과를 본 뒤 검토한 자료이며 블라인드 검증으로 주장하지 않는다.

## 후보 동작

- 문자가 없는 선 기반 표라도 이미지가 셀 안에 완전히 들어가면 격자를 보존한다.
- 이미지 객체는 해당 anchor 셀의 `blocks`에 배치한다. 병합 셀·원문 좌표를 보존한다.
- 중첩 표에서는 가장 작은 셀이 이미지를 한 번만 소유한다. 같은 크기의 경쟁 셀,
  여러 셀을 가로지르는 이미지와 표 외부 이미지는 임의로 셀에 배정하지 않는다.
- 이미지 바이트는 기존 `images` 옵션을 따르며 OCR을 새로 실행하지 않는다.
  이미지 경고와 문자가 전혀 없는 문서의 `NEEDS_OCR` 상태를 유지한다.
- 이번 변경은 텍스트 없는 선 기반 표가 대상이다. 기존 텍스트 표의 이미지 귀속이나
  무괘선 이미지 표는 확대하지 않았다.

## 검증

새 공고 첨부 12개(개발 8개·검증 4개)를 이전 사용 이력을 제외하고 수집했다.
DOCX 2개, HWP 7개, HWPX 2개, PDF 1개이며 신규 PDF는 개발 split이다.
검증 split에는 PDF가 없어 새로운 PDF 양식에 대한 블라인드 일반화 근거는 없다.
알려진 개발 PDF와 원문을 추가 검토한 회귀 PDF를 더한 14개를 동일 바이트·OCR/이미지
바이트 추출 끔·번호 구조 복원 켬으로 비교했다. 참조는 kordoc 4.22.15다.

| 검사 | 기존 Kory | 후보 | kordoc |
|---|---:|---:|---:|
| 비교 문서 실행 성공 | 14/14 | 14/14 | 14/14 |
| 원문 검토 두 페이지의 표 개수 | 0/2 | 2/2 | 0/2 |
| 같은 두 페이지의 행·열 | 0/2 | 2/2 | 0/2 |
| 원문 텍스트 조각 존재 | 779/781 | 779/781 | 779/781 |
| XML 원문 표 개수 | 4/4 | 4/4 | 4/4 |

각 분모는 별개의 부분 검사다. 전체 문서 정확도나 OCR 텍스트 복원률이 아니다.
새 표본 12개의 출력은 모두 동일했다. 고정 회귀 160개는 159개가 버전 표기를 제외하고
동일했고, `corpus_040`만 위에서 확인한 이미지 표가 추가됐다.

두 문제 문서는 정규화된 native 텍스트, 전체 이미지 객체(각 78개·215개), 경고가
전후 동일했다. 문제 표 안 이미지 31개는 셀에 배치되며 중복·삭제되지 않는다.

새 테스트는 병합·셀 귀속·원문 좌표·이미지 바이트 옵션·0/90/180/270도 회전·
이미지 전용 페이지·빈 격자·셀을 가로지르는 이미지·중첩 표를 검사한다.
기존 구현에서 7개 실패·2개 통과, 후보에서 9개 통과다.
기존 314개와 새 9개를 합친 **323개가 통과**했고 Ruff 검사·형식 검사도 통과했다.
gate가 별도로 실행한 기존 314개도 통과했다.

## 시간과 원래 gate의 미채택 사유

warm-up 1회 뒤 문서별 3회 중앙값의 합을 기록했다. 파일 읽기·프로세스 시작은 제외했다.
최종 측정은 회귀 실행과 겹치지 않게 수행했다.

| 동일한 최종 소스·14개 입력 | 기존 | 후보 | 후보/기존 |
|---|---:|---:|---:|
| 최초 3회 측정 중앙값 합 | 0.973177초 | 1.044007초 | 1.072782 |
| 별도 5회 확인 측정 중앙값 합 | 0.972087초 | 0.993452초 | 1.021978 |

개별 문서의 15%·10 ms 동시 초과 경고는 없었다. 전체 시간은 최초 +7.28%, 확인 +2.20%로
공유 호스트의 변동을 보였다. 최초 결과를 확인 결과로 덮어쓰지 않았다.
프로파일링도 보존했으며 이 자료로 보편적인 지연 보장을 주장하지 않는다.

자동 gate의 원래 결과는 `accepted=false`, `applied=false`이며 이 기록은 변경하지 않았다.

1. 최초 시간 합이 1.05배 제한을 초과했다. 현재 gate는 5회 확인으로 이 합을 대체하지 않는다.
2. 고정 회귀 출력의 완전 일치가 159/160이다. 원문으로 의도된 개선을 확인했어도 현재
   gate에는 이를 승인하는 예외 계약이 없어 고정 회귀 실패로 처리한다.

원문 검토 결과를 이유로 평가 코드·정답·정책을 완화하거나 이력을 재설정하지 않았다.
처음에는 스킬의 미채택 후보 적용 금지 규칙에 따라 후보를 보존하고 반영을 보류했다.
이후 사용자가 품질 개선과 속도 저하의 의미를 확인하고 두 조건의 예외를 `허용해라`고
명시적으로 승인했다. 이 승인은 이번 후보에만 적용하며 향후 gate 기준을 변경하지 않는다.

## 명시적 예외 승인 후 적용

현재 소스가 고정 baseline과 같고 후보가 측정한 hash와 같은지 검증한 뒤,
기존 `apply_source()`의 hash 검증·적용 경계로 `src/kory_parser/pdf.py`를 반영했다.
새 회귀 테스트 `tests/test_pdf_image_only_tables.py`도 함께 추가했다.
적용된 소스 hash는 최종 benchmark의 candidate hash와 동일하다. 검증한 동작을
유지하도록 이번 적용에서 버전 문자열이나 다른 파서 소스를 추가 변경하지 않았다.

원래 자동 gate 결과와 별도로 `user_authorized_application.json`에 사용자 승인,
예외 범위, 원래 gate 기록 hash, 적용 소스·추가 테스트 hash와 적용 상태를 기록했다.
자동 gate가 통과한 것으로 기록하지 않는다.

적용 후 전체 테스트 **323개 통과**, Ruff 검사·형식 검사 통과를 확인했다.
두 문제 원문을 현재 코드로 다시 파싱해 7행×4열·2행×4열 표를 확인했으며,
JSON 출력은 앞서 측정한 후보와 동일했다. 이 검사는
`post_apply_source_checks.json`에 기록했다.
