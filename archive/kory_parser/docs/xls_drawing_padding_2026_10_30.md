# XLS 도형 텍스트 패딩 복구 후보 — 2026-10-30

## 후속 검증과 반영 완료

사용자의 후속 요청으로 평가기의 실패 처리를 별도로 수정한 뒤, 기존 후보를 그대로
재검증해 **실제 파서에 반영했다.** 최종 gate는 `accepted=true`, `applied=true`이며,
반영 후 전체 테스트 **355개가 통과**했다. 아래의 최초 실행 기록은 중단 당시의 이력이다.

평가기 수정은 Python `parse()` 내부 예외를 구조화된 별도 측정으로 기록하고,
결과 JSON이 없는 실패를 판정 도구가 다시 예외로 처리하지 않도록 하는 것이다.
원문에서 개선이 확인된 대상 문서의 기존 파서 예외 복구만 인정한다.
시작·파일 읽기·timeout·후보/참조 구현 실패, 설명되지 않은 출력 누락은 계속 미채택이다.
새 평가기 테스트 15개가 이를 검사하며, 기존 테스트·정답·시간 임계값은 유지했다.
실패한 기존 파서의 가상 결과 JSON은 생성하지 않았다.

동일한 18개 문서와 정답, 고정 baseline·candidate 소스로 재평가했다.
앞서 정리했던 일반 성공 표본 8개는 다시 내려받아 기존 SHA-256과 일치함을 확인했다.
검증 도구는 재평가 전에 수정하고 실행 중 hash를 확인해 동결했으며,
새로운 블라인드 검증셋을 확보했다고 주장하지 않는다.

## 원문에서 확인한 결함과 후보

현재 Data DB를 읽기 전용으로 조회해 기존 사용 공고를 제외한 100개 공고의
첨부 후보 348개를 확보했다. 새 seed와 공통 사용 이력으로 18개를 내려받았으며,
개발 12개와 기존 이력에 없는 기관 family의 검증 6개로 나눴다.
형식은 DOCX 2개, HWP 3개, HWPX 4개, PDF 4개, PNG 2개, XLS 2개, XLSX 1개다.
자동 첨부 수집이나 운영 파싱 배포는 연결하지 않았다.

개발 문서 `r26bk01728570_000_01`의 원본 Workbook 스트림을 확인했다.
도형 텍스트 TXO 7개가 각각 서식 run 길이 24 bytes를 선언하지만,
서식 CONTINUE 레코드는 34 또는 38 bytes를 담았다.
기존 xlrd는 길이가 8의 배수라는 assertion에서 중단해 결과 JSON도 만들지 못했다.

후보는 기존 읽기를 먼저 실행한다. BIFF8 시트에서 assertion이 발생한 경우에만
해당 시트를 전용 Sheet 구현으로 다시 읽는다. 정상 도형 처리는 xlrd를 그대로 사용하며,
도형 서식의 마지막 CONTINUE에 선언 길이보다 많은 비정렬 바이트가 있을 때만
초과분을 제외한다. 셀 레코드를 변경하거나 전역 xlrd 클래스를 패치하지 않는다.
복구한 시트에는 `XLS_DRAWING_TEXT_PADDING` 진단을 남긴다.

후보 위치는 로컬 `.artifacts/cycle_2026_10_30_001/candidate/`다.
수정 모듈은 `src/kory_parser/xls_drawing_text.py`와 `office.py`,
새 테스트는 `tests/test_xls_drawing_padding.py`다.
검토용 `candidate.patch`와 기존 보호 파일의 불변 검증도 같은 실행 폴더에 보존했다.

## 적용을 보류한 이유와 다음 과제

기존 파서는 문제 XLS에서 중단해 `baseline.json`을 만들지 못했다.
benchmark는 이를 `EXECUTION_FAILED`로 기록했지만 gate는 해당 파일을 무조건 읽어
`FileNotFoundError`로 중단했다. 따라서 **정식 acceptance 결과는 생성되지 않았고
`--apply`도 실행되지 않았다.** report 기본 명령 역시 acceptance 결과가 없어 실패했다.
실패 로그를 보존하고 별도 compact summary·decision·cleanup 기록을 남겼다.
이를 정상 gate의 승인 또는 정책에 따른 품질 거절로 보고하지 않는다.

스킬의 `executor failure` 중단 조건을 적용했다. 평가기·정책을 보호하는 이번 사이클에서는
판정 도구를 바꾸지 않았다. 다음 작업은 결과 파일을 만들지 못한 기존 구현의 실패도
gate가 명시적인 미채택 결과로 기록하도록 별도 검증하는 것이다. 그 뒤 같은 고정 입력과
후보를 재검증해야 하며, 현재 후보를 승인된 개선으로 취급하면 안 된다.

PNG 2개는 OCR을 끈 Kory 두 구현에서 예상한 `NEEDS_OCR` 상태다.
kordoc 이미지 입력은 OCR 비활성 요청에도 OCR을 수행할 수 있으므로 실행 성공을
동일 조건의 이미지 품질 우위로 해석하지 않는다. 시간 비교에는 이 이미지와
기존 구현이 실패한 XLS가 포함되지 않았다.
XML·BIFF 부분 검사와 kordoc 일치는 문서 전체 정확도나 독립된 사람의 검토를 뜻하지 않는다.
