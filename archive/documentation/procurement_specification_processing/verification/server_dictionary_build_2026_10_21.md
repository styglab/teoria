# 컴퓨터 서버 표본 10건의 사전 구축 배치

현재 [사전 구축 배치](retired_semantic_batch.md)의 prepare → extract → link → integrate →
review → finalize 경로를 실제 서버 표본 10건에 적용했다. 이번 결과는 **검토 전 사전 초안**이다.

## 입력과 실행 방법

`semantic_corpus/server_01`부터 `server_10`까지 원본·저장된 kordoc native 결과·
OCR 비활성 파서 기록을 해시로 확인하고 새 배치에 고정했다. 파싱을 다시 실행하지 않았다.
이전 사전·추출 제안·Harness2 정답을 입력으로 사용하지 않았다.

현재 Codex가 원문을 읽어 문서별 대상·역할·관계·대표 원자 속성·원문 절과 의미 매핑
제안을 작성했다. 각 제안은 기존 CLI와 동일한 accept 검사를 거쳐 저장했다.
별도 Codex subprocess의 자동 추출 성능을 측정한 실행은 아니다. 검토 역시 현재
Codex의 원문 대조이며 독립 모델·사람 정답 검증으로 간주하지 않는다.

로컬 실행 루트는 `.artifacts/procurement_specifications/server_dictionary_2026_10_21/`다.
현재 revision은 **r2**이며 `batch_r2/`, `result_r2/`가 기준이다. 최초 초안에서
장비 점유 U와 랙 수용 U가 같은 속성 후보로 묶인 것을 검토 중 발견해 별도 속성으로
분리했다. 이전 초안의 검토·결과를 덮어쓰지 않았다.

| 문서 내 관계 | 85개 |

| 대상 유형 후보 | 23개 |
| 속성 정의 후보 | 25개; 이 중 15개는 복수 문서에서 관찰 |
| 관계 유형 | 3개 |
| 추가 정규화가 필요한 원문 절 | 473개; 원자 속성과 내용이 중복될 수 있음 |
| 미확인 이미지 영역 | 4개 |

95개는 서로 다른 표준 개념 수나 실제 납품 장치 수가 아니다. 473개 원문 절을 모두
원자 조건으로 정규화한 것이 아니며, 일부 긴 셀의 나머지 절은 상위 서버 문맥에
보존해 세부 대상 귀속이 남아 있다. 속성 수·매핑 수를 독립 정확도나 전체 회수율로
해석하지 않는다. unresolved 목록은 문서 이슈·조건 상태·검토 지적·coverage 등을
중복 기록하므로 행 수를 독립적인 의미 오류 수로 해석하지 않는다.

## 확인한 의미 구분

- 시스템 메모리와 GPU 메모리는 다른 대상 개념으로 연결했다.
- 같은 메모리 용량 속성을 재사용하되 총량/모듈당·장착/지원/기보유를 한정자로 보존했다.
- CPU당 코어 수와 시스템 합계, 기본 클럭과 Turbo 클럭을 구분했다.
- 서버 점유 높이와 랙 수용 높이를 별도 속성 정의로 분리했다.
- 기존 DDR4 모듈은 호환 대상이며 신규 납품 메모리로 계산하지 않았다.
- 별도 공급·미장착 NIC에 물리 장착 관계를 만들지 않았다.
- 미래 GPU 확장 대안은 지원 조건과 OR 그룹으로 보존했으며 장착 GPU 수에 합산하지 않았다.
- HBA의 32GB, 전원 110W는 원문을 임의 교정하지 않았다.

보류한 원자 속성은 SSD 곱셈 표현의 비교 범위, CPU의 기본/부스트 미지정 클럭,
TDP로 확정할 수 없는 전력, GPU 지원 전력 표현, HBA 32GB, SATA/12Gbps 병기를 포함한다.
보류를 없애기 위해 새로운 속성을 만들거나 값을 교정하지 않았다.

## 산출물과 검증

`result_r2/`에서 다음 파일을 읽는다.

- `report.html`: 문서별 대상·규격을 펼쳐 보는 결과와 공통 속성·보류 목록.
- `attributes.csv`: 속성 정의와 관찰·문서 수.
- `observations.csv`: 원문 관찰·대상·조건·한정자·표준 매핑.
- `dictionary.json`, `mappings.json`: 사전 초안과 전체 관찰 매핑.
- `components_with_specifications.json`, `document_graphs.json`: 문서별 구조.
- `unresolved.json`, `review.json`: 미해결 항목과 검토 기록.
- `readable_summary.json`, `validation.json`: 집계와 실제 결과 검증.

원본·입력 해시와 단계별 receipt를 재검증했다. 현재 코드에서 finalize를 다시
실행해 기본 최종 파일이 바이트 단위로 동일함을 확인했다. 실제 출력에 대한
의미 분리·보류·역할·OR 그룹 등 14개 검사를 통과했다. 이 검사는 독립적인 의미
정답 평가를 대신하지 않는다. 실행 코드·Harness2·DB·Registry·운영 배포는 변경하지 않았다.
