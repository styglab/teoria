# PDF 고도화와 엔진 비교 — Python 0.3.0

2026-10-20. `archive/teoria_docparse/`의 독립 패키지를 고도화했다. Python용 PDF
패키지를 활용하되 표·중첩·셀 출처를 보존하는 자체 구조화 단계를 결합했다.
활성 Platform·Pipelines·Prefect에 연결하지 않았다.

## 변경한 동작

1. **기본 PDF 해석을 한 번으로 통합**했다. pdfplumber의 layout device를 유지하면서
   같은 pdfminer interpreter에서 clipping 연산도 수집한다. 기존의 두 번 해석을
   제거했다. pdfplumber의 `_layout` cache에 연결하므로 lockfile 버전과 회귀 검사를
   함께 유지한다. 모듈 전역 monkeypatch는 하지 않는다.
2. **선 탐색을 좌표 인덱스로 변경**하고 표 bbox를 캐시했다. 셀마다 모든 선을
   훑거나 동일 표의 경계를 반복 계산하지 않는다. 점선의 조각 틈은 연결하되,
   셀 경계의 일부만 덮는 선을 전체 테두리로 인정하지 않는다. 원본 kordoc MIT
   `cell-edges.ts`의 coverage/slack 판정을 보완 이식했다.
3. **표의 빈 여백 행과 선 밖 들여쓰기 칸을 접는다.** 실제 선이 있는 빈 입력란과
   병합 칸은 구분한다. 기본 격자 유지 옵션을 지정하면 후행 열은 그대로 둔다.
4. **같은 쪽의 인접 양식 상자와 숫자 목록의 쪽 넘김을 복원**한다. 좌우 경계,
   문서 여백 위치, 번호 연속성과 중간 제목을 확인한다. 새로운 제목이 있으면
   독립 양식으로 유지한다. 두 페이지로 이어진 표도 셀별 출처와 각 쪽의 bbox를
   `Table.regions`에 유지한다. 모든 종류의 여러 쪽 표 연결을 완성한 것은 아니다.
5. **선택 PyMuPDF 경로**를 추가했다. MuPDF의 `rawdict` 문자와 `get_drawings()`
   벡터·클리핑을 Python 표 복원 단계에 넘긴다. PyMuPDF의 `find_tables()` 결과로
   전체 문서를 교체하지 않는다. 독립 탐지 probe에서 한컴 clipping·점선·중첩 표의
   누락이 확인됐기 때문이다. [공식 API](https://pymupdf.readthedocs.io/en/latest/page.html).
6. **깨진 글꼴 매핑을 무조건 삭제하지 않는다.** Unicode를 알 수 없는 글리프는
   fontTools로 실제 내장 outline을 확인한다. 윤곽이 없는 글리프만 공백으로 복원한다.
   확인할 수 없거나 회전된 페이지, native 추출 오류는 pdfminer로 되돌리고
   `PDF_BACKEND_FALLBACK`을 남긴다. JSON과 이미지 바이트 추출 계약도 유지했다.

## 같은 68개 문서에서의 결과

| 형식 | 문서 수 | 0.2.0 기본 | 0.3.0 기본 | 0.3.0 MuPDF |
|---|---:|---:|---:|---:|
| HWP | 21 | 21 | 21 | 21 |
| HWPX | 10 | 10 | 10 | 10 |
| PDF | 32 | 12 | 14 | 14 |
| DOCX | 1 | 1 | 1 | 1 |
| XLSX | 2 | 2 | 2 | 2 |
| PNG | 2 | 0 | 0 | 0 |
| **전체** | **68** | **46** | **48** | **48** |

성공한 PDF 29개의 원본 표 219개 중, **같은 순번에서 격자와 셀 내용이 일치한 표**는
0.2.0의 54개에서 기본 경로 **115개**, MuPDF 경로 **79개**로 늘었다. 표 개수가
다르면 순번 대응도 어긋나므로 최적 매칭이나 독립적인 표 정확도 지표는 아니다.
MuPDF의 속도 개선이 모든 문서에서 같은 표 구조를 보장하는 것은 아니다.

일치는 양쪽 성공, 정규화한 본문, 같은 순번 표의 행·열·anchor·병합 span·셀 텍스트가
모두 같은 경우다. 글꼴·이미지·조판·의미 정확도 전체의 동등성을 뜻하지 않는다.
OCR·수식 OCR·이미지 바이트 추출은 양쪽 모두 껐다. 입력 SHA-256, kordoc 4.22.15,
후보 소스 hash를 고정하고 실행 중 소스 변경을 검사했다.

주요 개선 사례는 `corpus_020`의 빈 여백 행과 `corpus_066`의 쪽을 넘는 숫자 목록
상자다. 기존 0.2.0에서 일치한 46개는 모두 유지했다. 주요 10개는 이 68개의 부분집합이며
입력 hash로 대응한 일치는 7/10이다. 별도 10개 독립 표본으로 합산하지 않는다.

[기본 경로 68개 결과](../verification/results/corpus_68_v0_3_0.json),
[MuPDF 경로 68개 결과](../verification/results/corpus_68_native_v0_3_0.json)에
문서별 숫자와 입출력 hash를 남겼다. 두 경로의 일치 문서 수가 같아도 모든 문서의
native JSON이 같다는 의미는 아니다. 이번 코퍼스는 개발에 사용했으며 독립 holdout이 아니다.

대표 PDF 6개를 고정하고 각 엔진에서 문서당 warmup 1회 뒤 3회 실행한 **중앙값**이다.

합계는 문서별 중앙값의 합이다. 6개는 무작위 표본이 아니며 전체 문서·다른 장비·운영
Prefect 처리량으로 일반화하지 않는다. 속도 우열을 추출 정확도 우열로 해석하지 않는다.

## 남은 차이와 선택 기준

- **원본과 차이가 전혀 없는 상태는 아니다.** 페이지 간 표 연결, 단일 셀의 연속성,
  서명란처럼 선 없이 정렬된 표, 도식의 읽기 순서에 차이가 남는다. 일부 PDF에서는
  MuPDF 경로와 기본 경로의 글꼴·순서 해석도 다르다.
- 이전에 확인한 `corpus_041/044`의 일반 법령 문장에 대한 원본의 표 오탐을 그대로
  모방하지 않았다. 원본과의 차이를 전부 Python 오류로 취급하지 않는다. 개별 원문
  확인은 [0.2.0 기록](difference_fixes_2026_10_20.md)에 있으며 전체 시각 검수는 아니다.
- 텍스트 없는 PDF 2개와 PNG 2개는 OCR off 상태에서 `NEEDS_OCR`다. 암호 PDF 1개도
  실패한다. 원본의 빈 본문 success와 같게 보이도록 성공 플래그를 변경하지 않는다.
- 기본 설치는 pdfplumber 경로다. native 경로는 `pdf_native` extra 설치와
  `ParseOptions(pdf_backend="pymupdf")` 또는 CLI `--pdf-backend pymupdf`로 선택한다.
- PyMuPDF는 [AGPL 또는 상용 라이선스](https://pymupdf.io/licensing)이며 선택 의존성에
  그 조건이 적용된다. 기본 설치에는 PyMuPDF가 필요하지 않다.
- 이 검증으로 Python이 원본보다 모든 문서에서 더 정확하거나 빠르다고 주장하지 않는다.

## 테스트와 설치형 패키지

- `pdf_native` extra 환경에서 테스트 **60개 통과**. 기본 설치에서는 선택 엔진 테스트를 skip한다. 점선/음영/중첩 표, 부분 테두리 오탐, 쪽별 출처,
  독립 문서의 잘못된 연결 방지, 실제 내장 outline을 이용한 빈 글리프 식별,
  native 실패·회전 페이지 복귀, 선택 의존성 누락, 이미지 추출을 확인했다.
- Ruff 정적 검사와 형식 검사 통과. wheel·sdist 빌드 및 격리 설치 확인.
- 기본 wheel과 `pdf_native` 설치 환경에서 외부 프로세스 실행을 막고 파싱을 확인했다.
- 실제 원문/native JSON과 모델·개인 환경은 배포물에 포함하지 않는다. OCR 코드는
  이번 변경에서 재평가하지 않았다. 운영 Prefect Job·배포 검증은 범위 밖이다.

  [빌드 및 설치 확인](../verification/build_artifacts_v0_3_0.json).
