# 공고 이해·재귀 구성 트리 파이프라인 검증

## 변경 이유

납품 품목을 먼저 평면 목록으로 분류하던 v2는 통합 시스템의 하위 구성품을 독립 납품
품목으로 과분리했다. 또한 identify JSON Schema는 복수 문맥 role을 허용하고 validator는
일부 role만 허용하여 네 샘플 모두 identify에서 실패했다. 이 기록은 성공 결과로 재분류하지 않는다.

v3의 처리 순서는 공고 구매 목적·통합 범위 이해 → 재귀 구성 트리 식별 → 구성 검토 →
각 엔티티의 속성 추출 → 동일 대상·귀속 정리 → 원문 검토 → 사전 초안 통합이다.
구성품은 엔티티이며 부모 관계로 계층을 나타낸다. 속성은 직접 대상에 붙인다.

## 구현과 검사

- `ItemInventory`에 구매 범위 요약·근거, 단일 category, 직접 부모·관계 근거를 추가했다.
- component와 service, 기보유·외부 대상을 구분한다. 구성 깊이에 제한을 두지 않는다.
- `parent_id`는 직접 부모, `owner_item_id`는 소속 납품 품목이다. 발주 묶음 아래에서도
  가장 가까운 납품 품목을 소유자로 유지한다.
- 불명확한 포함 관계와 소속은 candidate/ambiguous/null로 보존한다. 기보유 장비를
  대상으로 수행하는 서비스의 소속 납품 품목과 실제 서비스 대상을 구분한다.
- `review_structure`의 명백한 오류는 속성 추출을 차단한다. 모델 검토를 정답으로 보지 않는다.
- 추출 작업에는 모든 하위 구성품의 원문 구간을 합친다. 검토한 부모 관계를 그래프에
  보존하며 resolve가 제거할 수 없다. 구성 검토 결과도 최종 파일에 저장한다.
- 원문 ID는 명시한 `required_text_node_ids`만 허용한다. 빈 노드·표 컨테이너·이미지를
  텍스트 추출 구간으로 오인하지 않는다. 알려진 이미지 미확인은 별도로 보존한다.
- 노드 참조와 소속 오류를 관찰 ID와 함께 모아서 한 번의 수정 호출에 전달한다.

## 실제 네 샘플 실행

원본 `.artifacts/sample` 네 파일과 기존 OCR 비활성 파싱 결과의 해시를 확인했다.
원본 다운로드·재파싱·DB·Prefect·Runtime·Registry·Ontology 게시는 실행하지 않았다.

첫 v3 실행에서는 원문 범위에 빈 노드·이미지까지 넣은 응답과 수정 응답의 해시 복사
오류가 발생했다. 미확정 소속·기보유 장비 대상 서비스 정책과 허용 텍스트 ID 입력을
보완한 후 첫 실행을 중단하고 새 r2 배치를 준비했다. 원시 응답을 수작업 수정하거나
이전 예측을 새 실행의 결과로 대체하지 않았다.

- 첫 실행: `.artifacts/procurement_specifications/sample_composition_v3_2026_10_22/`
- 새 실행: `.artifacts/procurement_specifications/sample_composition_v3_r2_2026_10_22/`
- 새 실행은 동시 문서 4개, 호출 제한 900초, 계약 오류 수정 1회, 별도 모델 대체 없음이다.

단위 검사: `uv run --locked --project backend pytest backend/tests` 결과
**213 passed, 19 skipped**다. 기존 Prefect 그래프 생성 경고가 있다. 새 feedback 테스트에서 나타난 직렬화 경고는
테스트 입력을 Finding으로 명시해 수정했고 해당 테스트를 다시 실행해 통과했다. 이 수치는
추출 정확도가 아니다. 로컬 문서 링크 검사는 439개 링크·91개 문서에서 오류 0건이었다.

실제 결과는 실행 완료 후 아래에 기록한다. 구성 트리 식별 성공과 속성 추출·검증·통합
완료는 별도로 집계한다.


r2의 네 문서는 구성 트리의 계약 검사를 모두 통과했다. 그러나 구성 검토는 속성 추출을
모두 차단했다. 문서 1~3은 소프트웨어에도 호환용 `physical_component` role을 요구한
코드의 잘못 때문에 물리 부품으로 오인됐다. 문서 4는 하부 수납장·잠금장치의 실제 누락이
확인됐다. 차단된 실행을 속성 추출 성공으로 집계하지 않는다.

이를 고친 r3는 role을 일반 `component`로 바꾸고 물리 여부를 관계에만 표현한다.
문서 1~3은 이전 모델 결과의 해당 role만 category에 따라 기계적으로 변환했다. 명칭·근거·
부모·범위·수량·구성품 관찰은 변경하지 않았으며 신규 모델 식별 성공으로 집계하지 않는다.
기존 결과 해시·이전 context receipt를 검증하고 `role_projection.json`에 변환 이력을 남겼다.
문서 4는 실제 누락을 수작업으로 채우지 않고 원문과 이전 검토 제안으로 새 식별을 실행한다.
모든 문서는 새 계약에서 구성 검토를 다시 수행한 후 속성을 추출한다.

r3: `.artifacts/procurement_specifications/sample_composition_v3_r3_2026_10_22/`


r3의 문서 2는 role 변경 전 이름이 처리 reason에 남아 구성 검토가 한 번 더 차단됐다.
이를 원문 오류로 오해하지 않도록 해당 메모의 내부 role 이름만 일치시키는 새 revision을
만들었다. 원문 인용·명칭·구성품·부모·조건은 변경하지 않았다. 처리 메모 변환 이력은
`sample_02_r4/batch/processing_note_projection.json`에 보존한다.


실제 속성 추출에서는 별도 두 문제가 확인됐다. 환경감시 표의 '개수(식)' 머리글이 공통
구간에만 들어가 품목 추출에서 '식'이 누락됐고, 큰 문서는 품목 전체 추출이 900초를 넘었다.
관련 표 전체를 supporting context로 보존하고 검토된 주요 구성품 가지별로 추출하도록
수정했다. 원문 단위나 구성품 속성을 수작업으로 채우지 않고 새 revision에서 재추출한다.
이전 실험은 기존 계획으로 검증하며 새 실행은 table/subtree 기본 계획을 사용한다.

- 환경감시 표 재추출: `sample_01_r5/`
- 큰 문서 하위 트리 재추출: `sample_03_r6/`, `sample_04_r6/` 및 실패 시 추가 문서
- 여러 revision이 겹치는 동안도 실행 coordinator가 이전 활성 문서의 호출 슬롯을 예약해
  전체 동시 추론을 4개 이하로 제한한다.


환경감시 문서의 table 문맥 재추출(r5)은 16개 엔티티·50개 규격/조건·25개 관계를
정리했고 원문 검토 오류 0건·모호성 9건으로 통합·최종 저장까지 완료했다. 결과는
needs_review이며 사람 승인·게시·독립 정확도 측정은 없다. 공급표의 수량 단위는
8식·8식·1식·1식으로 보존하고 설치구역별 1set과 구분했다.
