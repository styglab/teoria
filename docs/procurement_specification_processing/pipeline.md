# FormatID 파이프라인과 Codex 사용

**FormatID — 규격서 기반 물품 구조화·분석**은 물품·구성품·구성 관계·규격·속성·조건을 원문 근거와 함께 추출·분석하는 업무 서비스다.
서비스 식별 표기는 `formatid`다. 현재 코드 소유 경로 `specification_processing`,
API 경로와 Prefect Flow·배포 ID는 기존 실행 계약을 유지한다.

원본 입력부터 결과 저장까지 아래 순서로 처리한다. 실행은 Prefect, 원문 해석은 파서와 Codex,
표준관리에서는 미해결 사전 의미도 Codex가 판단한다. 검증·승인 정책·표준 적용·저장은 코드가 담당한다.

## Prefect 실행 입력과 기본값

`Deployments → specification-standard-management → Run → Parameters`에서 입력한다.
기본 입력은 `classification_code`(세부품명 10자리, 필수)와 `target_specifications`(기본 30)다.
나머지는 배포 기본값을 사용하며 실행할 때 바꿀 수 있다. 실제 Flow 인자 이름은 다음과 같다.

```json
{
  "classification_code": "4321150102",
  "target_specifications": 30,
  "selection": {
    "strategy": "latest",
    "lookback_days": 365,
    "max_notices_to_scan": 300
  },
  "management": {
    "purpose": "dictionary_management",
    "auto_apply": true,
    "force_review": false,
    "holdout_documents": 5,
    "minimum_development_documents": 5,
    "max_held_source_ids": 0
  },
  "execution": {
    "concurrency": 2,
    "model_concurrency": 4,
    "model_timeout_seconds": 180
  }
}
```

| 설정 | 동작 |
|---|---|
| `selection.date_from`, `date_to` | 게시일 범위. 생략하면 실행일 기준 최근 365일, 날짜 끝날 포함 |
| `management.purpose` | `dictionary_management`(기본 사전 관리), `quality_evaluation`(읽기 전용 평가) |
| `management.baseline_dictionary` | 기준 사전의 URI·sha256. 평가는 필수. 사전 관리는 생략하면 현재 승인 사전을 사용하며, 지정하면 현재 사전과 일치해야 함 |
| `management.force_review` | 기본 `false`: 확인된 문맥 재사용. `true`: 기존 항목도 재검토. 사전 관리에만 사용 |
| `management.auto_apply` | 별도 문서 검증·의미 퇴행 없음·보류 수 한도를 통과한 변경 묶음만 자동 반영 |
| `execution.run_id` | 생략하면 Prefect 실행 ID로 생성. 직접 지정하면 동일 입력의 선정 목록 재사용 |
| `execution.artifact_root` | 생략하면 Worker의 `TEORIA_SPECIFICATION_ARTIFACT_ROOT`, 기본 `s3://teoria-artifacts` |
| `execution.model` | 생략하면 Worker의 Codex 설정 사용 |

분류를 지정해 보관된 물품 공고 DB의 최신 유효 차수를 게시일 내림차순으로 최대 300개 확인한다.
취소·다른 분류·게시일 없음은 대상에서 제외한다. 정기 공고 수집이나 보류된 수집 배포를 활성화하지 않는다.
분류가 여러 개인 공고는 특정 첨부에 한 분류를 임의로 적용하지 않고 제외한다.
파일명에 규격·시방·사양·specification이 있는 지원 형식만 후보로 삼고, 다운로드·형식 서명·해시 중복 검사를 한다.
이는 파일명 기반 후보 선정이며 본문이 실제 규격서인지 전부 판정했다는 뜻은 아니다.
ZIP이나 이름만으로 확인할 수 없는 문서는 자동 선정하지 않는다.

목표 수는 **공고 수가 아닌 중복 제거된 확보 파일 수**다. 독립된 파일 두 개는 두 개로 센다.
탐색 범위에서 목표 수를 채우지 못하면 확보한 수로 진행하고 사유를 남긴다. 파싱·추출 후 완료 문서 수와 부족 수를 따로 기록한다.
파일명 기준은 규격서처럼 보이는 첨부 후보 선정이며 본문 적격성을 보장하지 않는다. 01단계에서 명확한 공고문·빈 양식은 `not_specification`으로 제외하고, 혼합 문서는 기술·납품 요구 구간을 보존한다. 제외 문서는 확보 후보 수에는 포함되지만 추출·평가 완료 수에는 포함되지 않는다. 제외된 수만큼 자동 추가 확보하는 반복은 아직 없다.
부분 추출 문서는 품질 통과 수에 포함하지 않는다. 같은 공고의 첨부는 구축용·평가용에 나누어 넣지 않는다.
기본값은 완료 문서 중 구축용 최소 5개·평가용 최소 5개이며 부족하면 변경안을 저장하되 자동 반영은 보류한다.
실제 모델 기반 의미 검증이며 사람의 정답 평가나 전체 정확도 향상을 증명하지는 않는다.

`dictionary_management`는 사전이 비어 있든 기존 내용이 있든 같은 처리 경로를 사용한다.
기존 의미·문맥은 재사용하고 새 표현·변경 문맥을 판단해 필요한 정의·매핑을 추가·개정한다.
기존 `initial_dictionary`·`incremental_update` 입력도 이 이름으로 변환한다. 전체 재검토는 이름으로 결정하지 않고 `force_review`로 명시한다.
`quality_evaluation`은 고정 기준 사전에 연결한 결과를 저장하며 사전 정의·매핑을 변경하지 않는다.
`auto_apply: false`는 사전 관리 변경안을 저장하고 반영하지 않는다.

문서를 직접 지정하려면 같은 설정 객체를 `manifest`에 넣고 `documents` 목록을 추가한다.
이 경우 공고 DB를 조회하지 않고 입력 파일 순서로 처리한다. 기존 `SpecificationRun` 형식의 `manifest`도 유지한다.
`manifest`와 개별 Flow 파라미터를 동시에 수정해 제출하면 오류로 처리한다.
관리 API도 새 설정 객체를 기존 `manifest` 필드로 받는다. 이전 설명의 `request`는 실제 인자 이름이 아니다.
분류 없는 기존 샘플은 기존 명시적 문서 manifest 경로를 사용한다.

기존 의미를 참조하지 않고 새 사전 초안부터 구축할 때는 명시적 `SpecificationRun` manifest에서
`dictionary_rebuild_from_sources: true`, `dictionary_auto_approve: false`,
`dictionary_meaning_auto_approve: false`를 함께 지정한다. `mode`는 `standard_management`이며
과거 사전·근거 corpus 입력과 혼용하지 않는다. 원문 표현의 식별자는 재사용할 수 있으나 기존 의미 정의·매핑은
계획 입력에서 제외한다. 기존 사전 snapshot은 백업하고 새 정의는 rebuild 전용 key로 작성한다.
`draft_definitions.json`, `draft_mappings.json`, `changeset.json`은 검토용 제안이며 승인된 사전 snapshot이 아니다.
기존 사전 삭제·자동 승인·게시·전환은 하지 않으며 새 초안의 적용에는 별도 전환 검토가 필요하다.
재구축에서 기존 승인 의미로 되돌아가 표준 매핑을 성공 처리하지 않는다.

사전 계획의 형식·소유자·분류·단위 계약 오류는 원래 제안과 오류 위치를 저장하고
최대 한 차례 수정 요청한다. 수정 후에도 실패하면 `corpus_plan_contract_failed`로 보류하고
후속 문서 결과 저장을 계속한다. 단위가 있으면 측정 차원·대표 단위·허용 단위를 함께 지정하고,
대표 단위는 허용 단위에 포함돼야 한다. 관측 단위를 삭제하거나 임의 보완해 통과시키지 않는다.
`*_invalid_plan.json`, `*_validation.json`은 해당 사전 관리 batch에 보존한다.
`10 MHz~8 GHz`처럼 양끝에 단위가 있는 수치 범위는 별도 `unit_raw`가 없어도 값 안의
명시된 단위 표기를 검증에 사용한다. 알려진 단위로 온전히 표현된 범위에 한정하며 값·단위는
환산하거나 다시 쓰지 않는다. 임의 문장·모델명에서 단위를 추정하지 않는다.

04단계의 `extraction/table_attribute_context.py`는 같은 표의 명시 헤더에서 숫자 셀의 단위를
복원하고, 구매 수량의 부서·동별 하위 헤더를 조건으로 보존한다. 기존 관찰이 빠진 구분별
수량은 숫자 셀과 구매 행의 공급 대상이 하나로 확정될 때만 추가한다. 합계 계산·수량 전파·
새 대상 생성은 하지 않는다. 충돌하는 단위나 복수 대상 행은 추정하지 않는다. 값 셀의
정확한 근거와 헤더·단위 셀의 복수 근거를 함께 저장하므로 원문에서 확인할 수 있다.


선정·준비 산출물은 `specification_processing/<run_id>/`의 `document_selection.json`,
`management_batch.json`, `development_checkpoint.json`, `validation_checkpoint.json`에서 확인한다.
00–05 전체 추출을 먼저 보존하고, 구축·검증 입력을 분리한 다음 `<run_id>_apply`에서 기존 처리·사전 관리·완료 기록을 실행한다.
최종 실행의 Data DB에도 준비 산출물 참조와 확보·평가 요약을 남긴다. 새 배포나 별도 Flow를 만들지 않는다.
DB에 보관된 공고가 오래됐으면 그 범위 내 최신순이며, 외부 사이트의 현재 최신 공고를 보장하지 않는다.

| 04 | 속성의 대상·역할·범위 판정 | 해당 속성 원문 근거·독립 구매 행 귀속·ID를 검사하고 오류 사유와 함께 한 번 재판정. 불명확하면 unknown 유지 |
| 06 | 표준관리의 미해결 표현에 기존 개념 동등 연결 또는 새 로컬 정의 판단 | 별도 Codex 재검증과 코드 검증 통과 시 승인 정책에 따라 반영, 불명확·충돌은 보류 |

### OCR과 대상별 원문 문맥

Kory Parser의 `ocr=True`를 사용한다. 텍스트가 없는 PDF 페이지에서 OCR을 실행하며,
기존 텍스트를 가진 페이지와 Office·한글 문서는 파서의 원래 경로를 유지한다.
Worker의 별도 파서 환경에 OCR extra를 설치하고 PDF OCR 모델은 이미지 빌드 중 준비한다.
실행 사용자에게 패키지 디렉터리 쓰기 권한이나 런타임 모델 다운로드를 요구하지 않는다.

OCR 사용 가능 여부와 실제 사용 여부·페이지를 구분해 기록한다. 원문 node에는 파서의
페이지·좌표·인식 근거를 유지하고 해석 요청에도 전달한다. 읽지 못한 OCR 필요 페이지가
있으면 다른 페이지가 성공해도 부분 완료로 남긴다. OCR 성공이 표 구조나 의미 추출의
정확성을 보장하지는 않는다.

속성 조각에는 같은 행·열·제목뿐 아니라 기존 원문 귀속이 가리키는 품목 이름을 함께 제공한다.
독립 구매 행의 대상이 하나로 확인된 경우 요구 속성을 다른 구매 행에 붙이지 못하게 검사한다.
같은 행에 근거가 있는 복구 대상과 이미 확인된 하위 대상은 허용하지만, 이 검사로 구성 관계를
생성하지 않는다. 병합 셀의 공통 조건이 여러 구매 행에 걸치면 한 품목에 강제 귀속하지 않는다.
전체 구매 범위 root는 독립 구매 행 제약으로 사용하지 않는다.

속성 판정은 그 속성의 원문 node를 반드시 인용해야 한다. 같은 호출에 들어온 다른 속성의
근거만 인용하면 오류 사유를 전달해 한 번 다시 판정한다. 미해결 결과는 원문과 값을 보존하고
unknown으로 남긴다. 이 규칙은 원문 연결을 검사하며 의미 정확도 전체를 증명하지 않는다.

03단계에서 대상 누락을 보고하거나 미귀속 속성이 생긴 구간만 별도의 제한된 보완 대상으로 삼는다.
대상 보완은 문서당 한 번, 최대 24개 구간·새 대상 12개이며 입력 크기 상한도 검사한다.
원문에 실제 있는 이름과 위치를 검증하고 기존 ID·직접 구성 목록·납품 수량은 수정하지 않는다.
새 대상의 실제 제공 여부와 부모 관계는 자동 확정하지 않고, 해당 구간의 속성을 다시 추출한 뒤
04단계에서 별도로 검토한다. 같은 원문 관찰이 대상까지 확인돼 재추출된 경우에만 이전 미귀속
관찰을 대체한다. 보완 실패는 문서 전체 실패로 바꾸지 않는다.

한 단계가 한 번의 모델 호출이라는 뜻은 아니다. 문서 크기·구간 수·재판정에 따라 달라진다.
Codex는 제공한 원문과 문맥으로 JSON을 반환한다. 추론 호출에서 도구·파일·네트워크·위임을 금지하고,
코드가 스키마·원문 일치·ID·유형을 검사한다. 파이프라인 자체가 Skill을 읽어 실행하지는 않는다.

모델·동시 실행·시간 제한은 실행 입력으로 지정한다. 유효한 extraction_checkpoint를 재사용하면
01–04의 새 파싱·추론을 건너뛰므로 새 추출 품질 검증으로 표시하지 않는다.

## 엔티티·속성·관계 계약

### 물품과 관계

- 기준은 공급 목록 → 명시적 구성 목록 → 구조적 규격표 → 기술 절 순서로 선택하고 상세 단계에서 바꾸지 않는다.
  목차·절 제목은 대응할 대상을 찾는 단서이며, 선택한 목록과 별개의 최상위 구성 목록으로 합치지 않는다.
- 먼저 구매 범위와 독립 구매 항목을 고정한다. 현품설명서의 식품 행들을 하나의 물품 부품으로 묶지 않는다.
  시험 대상·설계 기능의 예·기존 설비·설치 장소를 실제 공급 대상과 구별한다.
- 유형은 물품(`product`), 원재료·재질(`material`), 장비·부품(`equipment`), 소프트웨어,
  작업·문서·묶음·미확정이다. 소프트웨어 자체도 구매 대상이 될 수 있다.
  구매 대상·구성품·포장 같은 역할과 대상 유형을 구별하며, 네 개 고정 범주로 모든 물품을 나누지 않는다.
  기존 장비 산출물의 `equipment`는 유지한다. 대상 수가 납품 물품 수는 아니다.
- `대상 → in_procurement_scope → 구매 범위`와 `하위 → component_of → 상위`는 다른 관계다.
- 원문 구성 근거가 있으면 두 관계를 함께 보존한다. 단순 표·절 배치로 구성을 만들지 않는다.
- 통합 물품의 명시적 구성 목록(`configuration_list`, `integrated_scope=true`)은
  `composition_inventory`에 root·직접 항목 ID·원문 순서·근거를 보존한다.
  상세 규격의 반복 제목은 기존 항목에 연결하고 추가 하위 대상이 이 목록을 건너뛰어
  전체 물품에 직접 붙거나 직접 항목이 다른 항목 아래로 이동하는 제안은 보류한다.
  04 단계의 구성 누락 검토에도 같은 경계를 적용한다. 단순 공급 목록·기술 절만으로
  닫힌 물리 구성 목록을 가정하지 않는다. 수량·속성·원문 scopes는 유지한다.
- 공급 목록(`supply_list`)은 구매 행·명시 수량·원문 순서의 기준이며 물리 구성관계의 상한선은 아니다.
  상세·설치 본문에 명시된 구성관계는 별도로 보존한다. 관계 추가가 구매 행·수량을 생성하거나 복제하지 않는다.
  본문의 언급이 기존 구매 항목과 동일한지 불명확하면 별도 원문 언급과 구성관계를 보존하고,
  양쪽 원문 근거가 있는 `same_target_as + ambiguous` 제안으로 동일성만 보류한다.
  기존 구매 항목과 정확히 같은 이름의 추가 대상은 이러한 별도 언급 근거가 있을 때만 허용한다.
  목록 밖 묶음이 명시적 `service_for`의 대상이고 공급 항목 아래에 포함된 근거가 없으면
  `work_scope_target` 역할로 보존한다. 유형을 바꾸거나 다른 이름의 공급 항목과 임의로 합치지 않는다.
- `inventory_assessment`에 기준 목록 확인(`confirmed`), 상세 사양 대체(`detail_fallback`),
  판독 실패(`reading_failed`), 판독 불확실(`reading_uncertain`), 미확정(`unresolved`)을 저장한다.
  목록이 파악되지 않았다는 사실을 원문에 목록이 없다는 확정으로 바꾸지 않는다.
  OCR 파서 프로세스는 실행당 한 개로 제한하고 본문 분류·모델 I/O는 요청의 동시 실행 제한을 따른다.
  초기 파싱은 이미 OCR을 켠다. PDF의 `INVALID_TABLE`/`TABLE_PARSE_FAILED` 진단에 페이지·영역이 있으면
  최대 3개 영역을 한 번, 총 90초 내에서 별도 OCR한다. 원문은 유지하고 복구 텍스트를 보충한다.
  OCR 텍스트 복구는 표 구조 복구를 뜻하지 않으며 확인 필요 상태를 유지한다.
  렌더링 영역이 없는 HWP/HWPX/DOCX 등은 복구 불가를 기록하고 임의 변환하지 않는다.
  미해결 판독 문제는 전체 추출을 완료로 표시하지 않는다. 다른 페이지의 진단은 확인된 목록을 무효화하지 않는다.
- 기본 추출 목표는 물품→구성품→하위 구성품과 각 대상의 속성이다. 상세 사양 절에서도 실제 제공 구성을 찾으며,
  `specification_for`를 구성 관계의 대체로 사용하지 않는다. 불특정 '부품' 같은 언급은 독립 구성품을 만들기보다 원문 조건으로 보존한다.
  04 단계는 기존 속성 판정 호출에서 누락된 구성 연결도 함께 제안한다. 별도 모델 호출을 늘리지 않는다.
  제안은 기존 ID·원문 구절·유형·순환 여부와 해당 대상의 요구 속성을 검증한 뒤 검토 전 관계로 추가한다.
  기존 장비·지원 능력·대안·작업·문서를 제공 구성으로 바꾸지 않으며, 속성값·수량과 기존 관련 관계를 수정하지 않는다.
- 작업은 `activity → service_for → 작업 대상`으로 표현한다. 문서·작업을 장비 부품으로 넣지 않는다.
- 원재료(`ingredient_of`)·재질(`material_of`)·포장재(`packaging_for`)·포장 단위(`pack_unit_of`)를
  부품 구성과 구별한다. 원재료·재질·포장재 관계는 해당 대상에서 관련 물품으로,
  포장 단위는 하위 단위에서 상위 단위로 연결한다. 포장당 수량을 총 구매량으로 전파하지 않는다.
- 소프트웨어 설치(`installed_on`)·펌웨어 대상(`firmware_for`)·의존(`depends_on`)·지원(`supports`)을 구별한다.
  설치·펌웨어는 소프트웨어에서 관련 대상으로, 의존은 의존하는 대상에서 필요한 대상으로,
  지원은 지원하는 대상에서 지원받는 대상으로 연결한다. 제공 대상만 분명하면 기존 `software_for`를 유지할 수 있다.
  명시된 소프트웨어 모듈 구성도 `component_of`로 표현하며, 기능 설명 자체를 모듈로 만들지 않는다.
- 제출·제공 문서는 `document → document_for → 문서가 설명·증명·지원하는 대상`으로 표현한다.
  이 관계는 설치·제출 완료나 정품 인증 성공을 뜻하지 않는다. 단순 지원·호환이나 모호한 설비를
  구성 관계로 확정하지 않는다. 관계 유형과 방향이 맞지 않으면 재판정 후 보류한다.
- 화면은 물품·구성품을 기본으로 하고, 구성 관계·포장 단위 관계는 별도 탐색 보기로 제공한다.
  05 추출 결과 검증·저장 단계는 문서별 `composition_hierarchy`에 기본 구성 범위를 기록한다.
  각 실제 구매 루트를 1계층으로 세고 `max_primary_levels=3`으로 고정한다.
  `root_ids`·`primary_entity_ids`·`detail_entity_ids`·`levels`는 이름이나 분류코드가 아니라
  근거가 있는 구성 관계로 계산하며, 재사용한 추출 결과에도 다시 계산한다.
  4계층 이하 대상은 세부 구성으로 구분하고 원래 엔티티·관계·수량·속성·근거를 보존한다.
  깊이를 맞추려고 부모를 건너뛰거나 실제 부품을 속성으로 바꾸지 않는다.
  화면의 기본 트리는 이 결과의 3계층까지만 표시하고, 그 아래는 접힌 '세부 구성'에서
  원래 부모와 속성·원문을 조회한다. 검색·전체 목록에서도 세부 대상을 찾을 수 있다.
  정책 필드가 없는 과거 결과에는 같은 깊이 기준을 화면에서 적용한다.
  이 정책은 기본 구성 범위를 제한하며 LLM 응답의 모든 대상 개수나 포장 단위 탐색의 깊이를 제한하지 않는다.
  근거가 있는 해석된 `component_of` 연결은 원래 부모 아래 '구성 관계 검토 중'으로 표시한다.
  이를 명시 관계로 바꾸거나 물리적 내부 포함으로 확정하지 않는다.
  부모가 보류·누락·다중 후보·순환으로 연결되지 않으면 그 하위 가지를 새 최상위 물품으로 올리지 않고
  '상위 물품·구매 범위 확인 필요'에 보존한다. 통합 구성 목록이 있으면 그 root와 항목 순서를 따른다.
  탐색 루트는 기준 목록 형식·분류코드가 아니라 원문에서 구매가 확인된 물품으로 선택한다.
  공급 목록의 행과 `supply_target` 역할을 사용하며, 단일 구매 물품이 root 자체인 경우에도 이를 포함한다.
  다른 구매 물품의 구성으로 연결된 대상은 그 아래에 표시한다. 기존 장비·작업 대상은 구매 루트로 올리지 않는다.
  연결이 보류·누락·다중 부모·순환인 항목은 독립 구매 물품으로 승격하지 않고 확인 필요 영역에 남긴다.
  구매 전체의 범위명은 접힌 '구매 범위·공통 규격'에서 조회하며 가상의 상위 물품을 만들지 않는다.
  분류코드로 없는 서버를 만들거나 원문에 없는 관계·수량을 추가하지 않는다. 기존 결과에도 재추출 없이 적용한다.
  기존 장비와 그 부품, 작업 대상 묶음과 그 하위 대상, 설치 지원·작업·문서는 접힌 관련 대상 영역에서 확인하며 전체·유형 필터로도 탐색한다.
  설치 지원을 삭제하거나 제공 완료로 확정하지 않으며, 기존 장비에는 '기존 대상'을 표시한다.
  연결 관계의 대상 버튼으로 관련 물품·소프트웨어·작업·문서를 탐색한다. 같은 대상을 복제하지 않는다.
  보고서는 대상 목록·유형·문서상 역할·관계·조건을 표로 보존한다. 모든 관계를 한 트리로 섞지 않는다.
- 제출 의무·제출 시점·설치 종료 등 기타 조건은 `requirements`의 원문 절로 보존한다.
  실제 물품 규격에 붙은 적용 조건은 속성의 `qualifiers_raw`에도 보존한다. 원문 절은 원자적 요구조건으로 확정한 결과가 아니며,
  과거 산출물에 없는 조건을 화면에서 새로 추정하지 않는다.
- 물리적 내부 포함은 명시 근거가 있어야 한다. 수량을 상위에서 하위로 전파하지 않는다.

잘못된 관계를 코드가 임의로 뒤집지는 않는다. 재판정 후에도 해결되지 않은 관계,
불확실한 동일 대상·유형·순환은 `held_relations`에 원래 방향·근거·사유를 남긴다.
엔티티·속성은 유지한다. 기존 checkpoint의 잘못된 작업/구성 유형은 재추출을 요구한다.

추출 완료 여부는 물품의 구성과 속성을 중심으로 판단한다. 통신(`sends_data_to`)·호환·의존·지원,
작업 대상(`service_for`)·문서 대상(`document_for`) 관계만 보류된 경우에는 그것만으로 추출을 partial로 만들지 않는다.
이들은 `supplementary_held_relations`에 집계하고 화면·보고서에서 부가 관계 검토로 구분하며 원문과 제안을 보존한다.
구성·규격 대상·동일 대상·종류 미확정 관계는 `core_held_relations`로 남긴다. 속성 실패·미귀속·미처리 구간과
문서 적격성 문제는 계속 부분 완료 사유다. 부가 관계의 의미를 자동 확정하거나 기존 실행 상태를 소급 변경하지 않는다.
이 구분은 사전 승인·표준 매핑·Ontology 게시 기준을 완화하지 않는다.

### 구성 보존과 재실행

02단계의 원문 검사 결과를 속성 처리의 기준 골격으로 사용한다. 03·04단계가 기존 대상의
ID·이름·유형·관계나 구매 목록·수량을 삭제하거나 바꾸면 검증 오류로 남긴다. 원문에서 새로
확인한 대상·관계는 추가할 수 있지만 고정된 직접 구성 목록을 다시 작성하지 않는다.
상위 장비의 속성으로 읽힌 문장도 구체적인 하위 장치 표제가 있으면 제한된 누락 검토 대상이 된다.
후보 표제만으로 구성품을 확정하지 않으며, 기존 대상·성능·프로토콜·재질 등을 새 장치로 복제하지 않는다.
새 대상의 부모·제공 수량은 이 검토에서 추정하지 않고 후속 원문 판정으로 확인한다.

운영 재실행은 `reuse_stage_checkpoints: true`를 기본으로 사용한다. 원본 SHA-256·고정 모델·
단계별 코드와 입력이 같은 파싱·구성·속성·판정 결과를 재사용한다. 파서 코드·설치 패키지도 확인한다.
상세 구성 추출 실패 전 확인한 구매 목록과, 완료된 속성 추출·판정 묶음은 따로 재사용할 수 있다.
실패·격리·미처리 구간이 있는 속성 단계나 응답 누락·검증 실패가 남은 판정 묶음을 완료 결과로 저장하지 않는다.
단위·치수축만 불명확하다는 이유로 근거가 있는 제품 귀속까지 지우지 않으며, 제품 자체도 모호하면 보류한다.

`reuse_stage_checkpoints: false`이면 이 중간 결과를 읽거나 쓰지 않는다. 모델이 고정되지 않아도
재사용하지 않으며, 평가 Flow는 항상 이 옵션을 false로 강제해 실제 새 추출을 비교한다.
재사용 단계는 결과의 `unresolved_extraction.reused_stages`, 판정 묶음은 `cached_batches`로 확인한다.
중간 결과는 객체 저장소의 `specification_processing/stage_checkpoints/v1/` 아래에 불변 JSON으로 두며,
원시 추론 로그·응답 대신 검사된 추출 관찰을 보존한다. 재사용은 AI 관찰을 승인된 구조나 게시 Ontology로
승격하지 않는다. 전체 실행의 DB 완료 체크포인트는 최종 산출물 저장 뒤에만 기록한다.

### 대상 명칭과 원문 표현

구매 목록의 원문 이름·ID·수량은 보존한다. 같은 상세 추출 호출에서 설명·영문 병기 등이 섞인
이름만 핵심 명칭 `name`과 원문 `name_raw`로 나눌 수 있다. 핵심 명칭은 원문 이름 안의 실제
연속 표현이어야 하며 모델·품종·가공 상태·함량처럼 물품을 구별하는 조건은 없애지 않는다.
특히 `product`·`material`은 가공 상태·부위·함량을 이름에서 제거하지 않도록 원문 이름 전체를 유지하고, 별칭·설명만 추가한다.
원문의 다른 명칭은 `aliases`, 용도·시험 구분 등은 `descriptions`에 원문 위치와 함께 남긴다.
표의 품명과 직접 대응하는 본문 표현처럼 같은 대상이라는 문맥이 있을 때만 별칭을 연결한다.
유사 이름만으로 별칭을 생성하거나 ID·독립 구매 행·수량을 합치지 않는다. 목차는 별칭의 직접 근거가 아니다.

화면은 핵심 이름을 기본으로 보여주고 원문 이름·다른 표현은 접어서 확인한다. 별칭 검색도
같은 대상 ID로 이동한다. 별칭과 설명은 원문 기반 추출 관찰이며 승인된 표준 용어나
Ontology의 동일성 선언이 아니다. 엄격한 고정 이름 평가와 별칭 근거 확인은 구별해 기록한다.

### 물품 규격과 기타 요구사항

아래 개선은 2026-11-01 Compose 운영 Worker에 반영했다. 알려진 원본 10개의 재추출·원문 대조·
자동 비교의 한계와 보류 항목은 [누적 재점검](../verification/specification_processing_recheck_2026_10_30.md)을 따른다.

순수한 개요·용도·작동 원리 설명은 본문 역할 `description`과 원문 절로 보존하고 속성 추출 대상에서 제외한다.
기능·성능·재질·보관·인증 등 실제 충족 조건은 비수치 문장이라도 규격으로 유지한다. 설명과 규격이 섞인
원문은 통째로 제외하지 않는다. 속성 판정에서 설명으로 분리하려면 숫자·단위·비교 조건이 없는 원문 절이어야 한다.
같은 대상·문단 계열의 연속 설명만 합치며 표 셀·새 항목·다른 대상 경계를 넘지 않는다. 결합 전 원문 근거는 모두 유지한다.

긴 셀의 속성 추출 조각은 줄 경계를 우선 사용하고 원래 문자 위치를 유지한다. 판정이 제공한 인용은
기존 근거 범위 안에서 유일하게 일치하고 값·단위·연산자·조건을 포함할 때만 `quoted_clause`로 좁힌다.
검증되지 않은 인용을 정확한 근거처럼 저장하지 않는다. 읽기용 `property_label`은 원문 속성명과 별도로
`model_suggestion` 출처를 기록하며, 원문 명칭·값이나 승인된 표준 의미를 바꾸지 않는다.

구매 목록에서 확인한 수량은 상세 추출에 함께 제공한다. 같은 대상·원문·값·동등 연산자이며 조건이 없고,
단위가 빠진 값 또는 별도 단위 셀이 목록 수량과 정확히 대응할 때만 기존 수량에 통합한다.
다른 위치·조건·대상·단위의 수량과 넓은 셀 안의 모호한 숫자는 합치지 않는다. 상위 수량을 하위 구성품에 전파하지 않는다.

결과는 물품·구성, 대상별 규격, 기타 요구사항으로 읽는다. 화면의 기본 목록은 물품·구성이며,
작업·문서는 전체 또는 유형 필터로 확인한다. 내부 유형·관계 구분은 유지하지만 모든 분류를
기본 화면의 별도 묶음으로 펼치지 않는다. 조회 범위와 대상 유형은 별도 필터다.
세부 유형 필터는 기본으로 접고 해당 문서에 나타난 유형만 제공하며, 조회 범위를 바꾸면 유형 선택을 초기화한다.
구매 기준 확인 상태와 대상별 구매 기준 수량을 보여주며, 별도 수량이 없으면 기재 없음으로 표시한다.
하위 구성·설치 대상에 상위 구매 수량을 전파하지 않는다.

일반 법령 준수·안전 원칙·계약 책임·규정 우선순위는 본문 분류의 `general_requirement`,
납품·설치 작업·보증·제출 조건은 `delivery_requirement`로 식별한다.
두 종류 모두 `requirements`의 `source_clause`, `category: other`에 원문과 근거를 보존하고,
화면과 보고서에서는 문서 단위의 접힌 **기타 요구사항**으로 보여준다.
수행자·행위·강도로 재분해하거나 별도 모델 호출로 일반 의무를 구조화하지 않는다.
기타사항에 대상 ID가 배정되지 않아도 원문을 확인할 수 있고, 세부 분해 여부를 물품 추출의
`partial` 사유로 사용하지 않는다. 이전 `obligation` 산출물도 원문 중심으로 표시한다.

하중·치수·재질·세척성·안전 성능·인증·설치 전압/호환성·식품 보관·소프트웨어 이용 조건처럼
물품 자체를 제한하는 내용은 `technical_requirement`다. 숫자 유무나 법령·안전이라는 단어만으로
기타사항에 넣지 않는다. 기술 조건과 일반 조항이 한 원문 node에 섞이면 기술 조건을 추출하고
전체 원문도 보존한다. 분류 실패·불확실한 본문은 계속 추출 대상으로 유지한다.

반복 제목·대상 언급은 번호·공백을 정리한 명칭이 원문 근거가 있는 기존 대상 하나와 정확히
일치하고 수치 비교·의무·조건 표현이 없을 때 `repeated_target_mention`으로 기록한다.
동명 대상이 여럿이거나 새 사양·의무가 붙은 문장은 이 규칙으로 처리하지 않는다.
“아래 상세사양 참조”처럼 상세 사양·규격을 가리키기만 하는 독립 안내 문구는
`specification_reference`로 기록하고 속성 누락에서 제외한다. 이 상태가 참조 대상의 추출 완료를
뜻하지는 않는다. 실제 상세 규격은 각각 검사하며, 수치·의무·조건을 함께 적은 참조 문장은 제외하지 않는다.
그 수는 `unresolved_extraction.specification_references`로 보존한다.
`unresolved_extraction`에는 규격 누락(`missing_requirement`), 대상 언급 미확인
(`unresolved_target_mention`), 관계 보류와 기타 원문 조항 수를 구분해 남긴다.
기존 의미 판정에서 공통 준수 조항이 속성으로 잘못 추출됐다고 확인하면 전체 원문과 근거를
기타사항으로 보존하고 `application_scope: unspecified`로 남긴다. 이는 모든 물품에 적용한다는 뜻이 아니다.
수치·단위가 있는 기술 규격을 이 경로로 숨기지 않는다. 대표 ID가 실제 물품이면 그 물품 자체의
구조·재질·마감·기능 조건은 해당 ID와 물품당 범위에 연결할 수 있다. 이는 모든 하위 물품에 같은
조건을 적용하거나 복제한다는 뜻이 아니다. 원문에서 특정 부분을 한정하면 그 표현과 근거를 유지한다.
대표 ID가 독립 물품들의 구매 범위 묶음이면 불명확한 개별 사양을 여기에 몰아넣지 않는다.
원문에서 대상을 확인하지 못한 구체적 규격은 미확정으로 남긴다.
실제 기술 규격 누락·귀속 미확정·실패·격리·관계 보류는 계속 `partial`의 근거다.
이 집계는 문서 전체 정확도나 재현율을 의미하지 않는다.

### 속성과 근거

원문 값·단위·연산·한정 조건을 보존한다. 모델명·기보유 제품·지원 한도를 신규 납품 성능으로 바꾸지 않는다.
수치 단위 보완은 같은 구절의 값 바로 뒤에 명확히 붙은 알려진 단위만 사용한다.
04 의미 판정 후에도 단위가 비어 있으면 원문 값의 정확한 위치에서 바로 이어지는 단위를
확인한다. `8‑코어`처럼 숫자와 단위 사이의 공백·하이픈은 허용하되 줄을 넘거나 다른
구절을 검색하지 않는다. 같은 숫자가 반복되면 검증된 값 위치가 없을 때 복원하지 않는다.
기존 단위·대상·값·연산자·조건은 수정하지 않고 추가 단위의 문자 위치를 근거에 남긴다.
`코어`·`스레드`의 원문 표기는 유지하며 비교용 단위만 `core`·`thread`로 정규화한다.
최종 귀속 후 대상·값·조건·역할·범위·원문 근거가 모두 같은 관찰만 합치고 원래 ID를 남긴다.
다른 위치의 반복 진술이나 상충 조건은 보존한다.

03·04는 절·표·상위 문맥을 선택해 전달한다. 전체 원문을 처음부터 품목명 목록으로 걸러내지는 않는다.
02에도 원문 제목 레벨에 따른 절 경로와 표 ID·행·열·병합 범위를 전달한다. 셀 안 문단에는 상위 셀 좌표를 연결한다.
목차는 `table_of_contents`로 식별해 `contents_nodes` 탐색 문맥으로 별도 전달하고, 물품·수량·관계의 직접 근거로 사용하지 않는다.
표의 품명·규격·총량·단위를 대응시키며, 같은 표에 있다는 사실로 대상 간 소유·구성을 확정하지 않는다.
식품의 함량·원산지·보관, 의류의 혼용률·치수, 자재의 규격·품질, 소프트웨어의 이용 조건도 사양이다.
물품당(`per_item`)·포장당(`per_package`)·명시 기준량당(`per_reference_quantity`)·구매 행/로트 전체(`batch_total`)를
장비의 부품당·프로세서당·시스템 전체 범위와 구별한다. 함량의 기준량은 `qualifiers_raw`에 보존하고 계산·환산하지 않는다.
파서에서 사라진 정보는 추출기가 복원했다고 표시하지 않는다. 기본 파싱은 OCR을 사용하지 않는다. 텍스트가 없는 스캔은 `needs_ocr`, 파서 프로세스 오류는 안전한 예외 유형과 함께 별도 기록한다.

## 사전과 표준 적용

06 단계는 원문에 나온 표현을 조회·등록하고, 승인된 의미 매핑이 있으면 표준 정의를 가져온다.
원문 명칭이 없는 속성은 내부 영문 후보명을 원문 표현처럼 등록하지 않는다.
새 동의어·표준 의미를 이름 유사도만으로 확정하지 않는다.

표준관리 모드에서는 문서가 들어올 때마다 기존 사전과 문맥을 비교한다.
현재 승인 정의 개정으로 이미 확인된 문맥은 재사용한다. 숫자만 달라진 경우 같은 문맥으로 인식할 수 있으며,
표현·소유 물품·역할·범위·조건·단위가 달라지면 관련 과거 추출 결과를 Data DB의 참조로 찾아 checksum을 확인한다.
Codex는 현재 문서와 관련 과거 근거를 함께 보고 기존 개념 연결, 새 정의, 정의 개정과 영향 매핑을 판단한다.
별도 검증을 통과한 변경 묶음만 인증된 Admin API로 원자적으로 반영한다.
`dictionary_meaning_auto_approve: false`이면 변경안을 저장하고 자동 반영하지 않는다.
과거 근거 누락·checksum 불일치·판정 충돌은 보류하고, 해당 문맥에 기존 의미를 임의로 적용하지 않는다.

문서처리 모드는 지정한 `dictionary_standard` URI·checksum의 고정 사전을 사용하고 이 증분 관리 경로를 실행하지 않는다.
로컬 사전 승인은 Published Ontology 게시가 아니다.

07 단계는 다음 두 연결을 구분해 저장한다.

| 연결 | 결과 |
|---|---|
| 사전의 승인된 개념 매핑 | `dictionary_meanings`, `dictionary_concept_ref`, 정의 개정·매핑 ID |
| 고정 표준/프로파일 적용 | 표준 버전·URI·checksum과 관찰별 적용/보류 |

사전 개념 ID와 Published Ontology Stable Concept ID는 다르다.
기본 `source_only`는 미확정 의미를 후보로 남긴다. 분류값만으로 분야 규칙을 켜지 않는다.
과거 `server` 규칙은 명시적인 호환 설정이며 현재 운영 물품 사전이나 활성 서버 Capability를 뜻하지 않는다.
상세 내용은 [사전](../platform/goods_dictionary.md)과 [프로파일](normalization_profiles.md)을 따른다.

사전 관리는 처음 입력한 문서와 이후 추가 문서에 같은 06 단계를 사용한다. 여러 문서의 extracted.json을 함께 입력할 수도 있다.
`dictionary_reconcile`은 이미 확인된 문맥도 다시 검토하는 옵션이며, `dictionary_corpus`는 추가 근거를 지정할 때 사용한다.
사전 안내의 `dictionary-maintain` 명령으로 묶음 개정도 실행할 수 있다.
개정과 영향 매핑을 함께 검증·반영하고 사전 스냅샷을 내보낸다. 문서처리는 `dictionary_standard` URI·checksum으로 사전 버전까지 고정할 수 있다.

## 저장 위치와 최소 산출물

| 산출물 | 내용 |
|---|---|
| `sources/` | 원본 파일 |
| `extracted.json` | 표준화 전 대상·관계·속성·원문·보류 |
| `dictionary_candidates.json` | 원문 표현 등록 후보와 근거 |
| `dictionary_bindings.json` | 등록·재사용·보류 판정 |
| `dictionary_semantic_decisions.json` | Codex 정의·매핑 판단, 재검증·자동 승인/제안/보류와 ID |
| `source_term_alignment.json` | 원문 등록과 표준 개념 연결 |
| `meaning_candidates.json` | 표준관리의 미해결 의미 후보 |
| `normalized.json` | 고정 표준 적용과 사전 연결 결과 |
| `index.md` | 사람이 보는 트리·속성·근거·보류 보고서 |

운영 본문은 MinIO의 `s3://teoria-artifacts/specification_processing/<run_id>/`에 저장한다.
화면 업로드 원본은 `s3://teoria-artifacts/specification_inputs/`에 저장한다.
`file://` 저장은 명시적으로 지정한 개발·테스트 경로로만 사용하며 운영 기본값은 S3다.
표준관리의 로컬 표준 초안은 `standards/<version>/standard.json`에 별도로 저장한다.
Data DB에는 실행·문서별 요약·URI·checksum만 저장한다. [저장소 기준](../pipelines/database.md)을 따른다.

다른 내용으로 같은 객체 키를 덮어쓰지 않는다. 모든 산출물 저장 후 완료/부분완료 상태를 기록한다.
파싱·추출·판정의 선택된 중간 결과는 `diagnostics/<종류>_<sha256>.zip`으로 묶어 MinIO에 저장한다.
모든 S3 업로드는 읽기 재검증으로 SHA-256 일치를 확인한다. 정상·일반 실패 종료 시 진단 저장이 성공하면 로컬 작업 폴더를 삭제한다.
저장·검증 실패 또는 원본 업로드 확인 전 실패 시 작업 폴더를 보존하고 오류에 위치를 남긴다.
임시 프롬프트·스키마·캐시는 진단 묶음에서 제외한다. 강제 종료 시 정리는 보장하지 않는다.
일반 실행의 원본·최종 산출물·진단 묶음은 보존하며 실행 종료만으로 MinIO 객체를 지우지 않는다.

## 실행 방법

화면 사용은 [FormatID 사용 안내](../platform-guide.md#규격서를-처리하려면)를 따른다. CLI는 다음과 같다.
실행 전에 Data DB·Prefect·Codex 인증·파서 Python·Admin 작성 API를 [환경 설정](../deployment/configuration.md)대로 준비한다.

```json
{
  "run_id": "specification_example_01",
  "mode": "standard_management",
  "model": "gpt-6.1-sol",
  "model_timeout_seconds": 600,
  "artifact_root": "s3://teoria-artifacts",
  "documents": [{
    "document_id": "equipment_01",
    "source_uri": "s3://teoria-artifacts/specification_inputs/<업로드_문서_ID>.hwpx",
    "filename": "equipment.hwpx"
  }]
}
```

```bash
uv run --project backend --locked --group orchestration \
  teoria-pipelines specification run --manifest /data/run.json
```

컨테이너 실행에서는 컨테이너가 읽을 수 있는 경로를 사용한다.
분류가 없으면 생략하고, 있으면 검증된 10자리 값을 `classification_code`로 지정한다.
`document_processing`에는 `standard.uri`와 파일 전체의 `standard.sha256`이 필수다.
입력·코드가 달라지면 새 run_id를 사용한다. 저장된 실행의 다른 내용 덮어쓰기는 거부한다.

## 선택적인 상위 표준 작성

`procurement-standard-workflow`는 기존 처리와 Admin 작성 API를 연결하는 상위 조립이다.
새 문서 처리 방식이 아니며 승인된 기준 프로파일이 필요하다.
이 경로를 명시적으로 실행하면 Admin API의 의미 제안에서도 Codex를 사용한다.
일반 06 사전 조회·07 표준 적용 자체의 모델 호출과 혼동하지 않는다.
[프로파일·상위 작성 절차](normalization_profiles.md)를 따른다.

## 검증 범위와 남은 한계

실행 완료, 원문 적합성, 업무 의미 정확도는 구분한다. Prefect Completed여도 문서는 partial일 수 있다.
현재 원본 처리와 Worker 반영은 [운영 검증](../../archive/documentation/verification/goods_relation_deployment_2026_10_28.md),
고정 원본 비교의 한계는 [평가 기록](../../archive/documentation/verification/goods_relation_repair_2026_10_28.md)에 있다.
별칭·동일 대상·조건 귀속·표준 의미 확대와 새 물품 Runtime 연결은 후속이다.

추출 개선은 [평가 절차](evaluation.md)를 따른다. 자동 공고 첨부 수집·참가자격 판단은 연결하지 않는다.
이전 실행 설계는 [보관 기록](../../archive/documentation/procurement_specification_processing/pipeline_2026_10_27.md)에서만 확인한다.

## 증분 관리 산출물

- `dictionary_incremental.json`: 재사용·반영·보류 결과와 사유.
- `dictionary_related_context.json`: 관련 과거 문서와 불러온 추출 참조.
- `dictionary_history/`: 영향 검증에 사용한 과거 관찰 부분집합.
- `dictionary_release.json`: 현재 실행에 적용하는 승인된 사전 스냅샷.

변경이 필요하면 maintenance 산출물에 변경안·검증·적용 결과를 저장한다.
Data DB에는 파일 참조와 확인된 문맥의 해시·정의 개정 ID를 저장하며 완료 실행만 재사용한다.
과거 파일 조회는 최대 100개이며 영향이 넓어지면 한 번 추가 조회·재판정하고 미해결은 보류한다.

## 본문 역할·품질·근거 가용성

본문 분류는 원문을 변경하지 않는다. 제목·작성 지침·입찰 절차·문의 구간은 요구조건 추출에서 제외하되 원문과 판정은 보존한다.
불확실한 구간은 계속 전달하며, 실제 납품·설치·교육·보증·제출 문서 의무는 단순한 제목이나 문서 명칭으로 대체하지 않는다.
인접 노드로 끊긴 문장은 같은 절의 문맥으로 전달한다. 숫자·원문 offset·근거 문자열을 합성하거나 자동 수정하지 않는다.

누락 결과는 기술 요구·납품 의무·대상 명칭·미분류별로 기록하고, 관계 보류도 종류별로 기록한다.
속성 역할 unknown과 범위 unknown, 대상 미배정을 각각 기록한다. 기존 보류 관계를 자동 확정하거나 품질 게이트를 완화하지 않는다.

사전의 `dictionary_evidence_corpus`는 이번 실행에서 이미 확보된 과거 의미 재검토용 근거다.
구축용 입력 수·독립 평가 수와 별개이며, 평가 문서 및 같은 공고의 첨부를 포함하지 않는다.
관련 원본 해시는 이 근거에서 먼저 찾고 부족한 경우 과거 Data DB 참조를 조회한다. 근거 해시·분류·평가 분리를 검증한다.
`document_assessment.json`, `failure.json`, `coverage.json`과 수락한 중간 결과는 MinIO diagnostics에 보존한다.
원시 모델 응답과 파서 stderr 본문은 영구 진단에 복제하지 않는다.

공고문의 일반 계약 조건과 구매 수량만으로 기술 규격이 있다고 보지 않는다. 양식에 물품명만 있는 경우도 마찬가지다. 실제 기술 조건과 불확실한 구간은 계속 보존한다. 모든 명시 입력이 대상 제외라면 실패 0·제외 수를 기록해 실행을 완료하며, 실제 파싱 실패와 혼동하지 않는다.

## 문서 탐색 색인과 결과 projection

입력의 파일명·원문 URI/checksum·공고번호는 `specification_processing_inputs`에 저장한다.
완료 checkpoint 전에 문서별 `documents/<document_id>/result.json`을 객체 저장소에 저장하고
DB에는 참조만 등록한다. 목록 조회는 본문을 읽지 않고 분류·원문 checksum·공고별로 재처리를
묶으며, 최근 실행 상태와 마지막 정상 결과를 각각 제공한다. 다른 내용의 파일은 별도 버전이다.

기존 결과는 운영 Worker에서 `teoria-pipelines specification index-catalog --limit 100`으로
명시적으로 보강한다. 허용된 저장소의 checksum 검증 산출물만 읽고 문서별 projection 저장 후
메타데이터와 참조를 transaction으로 등록한다. 원본 관찰이나 Published Ontology를 변경하지 않는다.
CLI 출력은 성공·실패 실행 수만 제공한다. 개별 조회 projection은 5 MiB 미리보기 제한을 따른다.
