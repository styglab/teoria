# 입찰체크 조달 탐색 계약 계획

이 문서는 2026-10-13 합의하고 Runtime bundle `2026.10.13.1`에서 처음 제공한 계약이다.
현재 호출 가능한 Capability는 [입찰체크 연동 계약](bid_check_capabilities.yaml)의
`capabilities`와 배포된 Runtime discovery로 확인한다.
입찰체크 backend의 호출 코드 위치는 이 저장소에서 검증하지 않았으며, 현재 의미는
이 저장소의 Registry와 [계약 집계 기준](../domains/public_procurement/contract_aggregation.md)을 기준으로 한다.

## 이름과 책임

| Capability | 변경 | 책임 |
|---|---|---|
| `autocomplete_procurement_entities` | 신규 | 선택용 이름·번호 후보와 검증된 필터 반환 |
| `get_procurement_network` | 신규 | 제한된 관계 그래프와 링크별 집계 반환 |
| `get_organization_company_relationship` | 기존 확장 | 기관–업체 관계의 집계와 근거 페이지 조회 |
| `analyze_procurement_field_market` | 신규 | 공식 분야의 수집 범위 내 시장 전체·연도별 집계 |
| `get_procurement_classification_catalog` | 신규 | 공식 분류체계·코드·계층 조회 |
| `get_procurement_region_filter_options` | 신규 | 실제 지원하는 지역 기준과 선택 가능한 코드 조회 |

`get_procurement_relation_detail`은 추가하지 않는다. 같은 기관–업체 관계를 조회하는
두 public Capability를 만들지 않는다. `get_company_coparticipation_relationship`은
두 업체의 동시 참여 공고 근거를 페이지 조회하는 화면이 필요할 때만 추가한다.
현재 신규 구현 범위에는 포함하지 않는다.

현재 네트워크와 분야 시장은 `contract_event_company_ledger`가 보유한 계약 관계만
집계한다. 낙찰·관측 참여·동시 참여·공동수급 관계가 해당 읽기 모델에 없으면 응답의
`coverage`에 `not_in_read_model`로 표시한다. `region_basis=participation_restriction`은
계약에 연결된 공고의 구조화 참가 지역제한을 기준으로 적용한다. 업체 소재지는 개별 업체
프로필에서 조회할 수 있지만 일괄 읽기 모델이 없으므로 지역 필터 기준으로 지원하지 않는다.
공식 분류 카탈로그는 공고 원천에서 실제 관측된 공식 코드 범위다.

| 기존 Capability | 재사용 경계 |
|---|---|
| `search_bid_notices`, `search_public_organizations`, `search_companies_by_name` | 각 대상의 검색 계약 유지; 자동완성은 선택 후보만 제공 |
| `analyze_company_procurement_profile`, `analyze_organization_procurement_profile` | 선택한 업체·기관의 프로필 패널; 네트워크에서 노드마다 반복 호출하지 않음 |
| `analyze_company_competitors` | 동시 참여업체 목록과 사건 집계 정의; 네트워크도 동일한 정의 사용 |
| `get_bid_notice_relationship_context` | 특정 공고의 관계 맥락; 범용 2단계 네트워크로 확장하지 않음 |
| `analyze_bid_participation_context` | 특정 공고 게시 직전 기관·분야 분석; 분야 전체 시장 분석과 구분 |
| `search_bid_related_projects` | 특정 공고와 관련된 과거 계약사업 검색 유지 |

내부 SQL·식별 정규화·집계 규칙은 재사용한다. 같은 입력과 의미의 결과를 이름만
바꿔 public 계약으로 중복 제공하지 않는다. 분류 카탈로그는 공식 사전이며, 관측된
계약에서 뽑은 분야 분포와 구분한다. 검색 인덱스와 응답 projection을 Business
Ontology Object로 추가하지 않는다.

## 자동완성

- `query`, `types`, `limit`(기본 8, 최대 20), `cursor`를 지원한다. limit은 한 응답의
  전체 후보 수에 적용한다. 대상은 공고·기관·조달업체·공식 분야/품목이다.
- Runtime이 읽는 내부 검색 인덱스만 사용한다. 외부 기업정보 API와 실적 전체 집계를
  호출하지 않는다. prefix·초성·번호 검색을 지원한다.
- 후보는 안정적인 type/id와 이름·번호를 반환한다. 공고 번호의 차수 구분과 업체
  식별 정규화는 기존 식별 계약을 유지한다.
- 공고 후보에 공고기관·수요기관의 역할별 코드·명칭, 업무구분, 공식 분류체계·코드,
  원천에 명시된 소재지·지역 기준을 담는다. 누락값은 `null`로 보존한다.
- 공고의 참가 지역조건은 `filter_values.region`에
  `{basis: participation_restriction, codes: [...], match: any}`로 반환한다. 복수 허용
  지역을 단일 코드로 축약하지 않으며 `context.region_conditions`에 코드·명칭을 보존한다.
  조회 Capability에는 이 값을 `region_codes`로 전달하고 하나인 경우 기존
  `region_code`도 사용할 수 있다.
- 자동 적용 가능한 조건과 누락 또는 미지원 조건 및 그 이유를 구분해 반환한다.
  값이 있어도 해당 필터를 Runtime이 지원하지 않으면 자동 적용하지 않는다.
  제목으로 분야를 추정하거나 기관 소재지를 참가 지역 제한으로 사용하지 않는다.
- 후보 클릭 후 별도 시장 분석 없이 검증된 필터만 적용할 수 있어야 한다.
- 정규화한 질의 캐시를 사용하되 번호와 공식 코드의 의미를 보존한다. 캐시 키는
  types·limit·cursor·권한 범위·인덱스 버전을 포함한다.
- 요청 취소와 늦게 도착한 응답의 화면 반영 방지를 지원한다. 서버·DB 작업으로의
  취소 전파 범위도 검증하고 문서화한다.
- 정렬 우선순위·동점 처리·cursor의 버전 결속과 만료 동작은 구현 전에 확정한다.

## 네트워크

`root_type/id` 또는 `field_code` 기반 시작점, 분야, `work_type`,
`region_basis/code`, `period_from_year`, `period_to_year`, `depth`(최대 2),
`first_hop_limit`, `second_hop_limit`을 입력으로 계획한다. 노드 ID는 이름이 아닌
기존 기관 코드·정규화한 업체 식별자·공식 분류 식별 계약을 따른다.

다음 입력 조건은 실제 schema 발행 전에 확정한다.

- 지원하는 root type과 root별 확장 경로, 공고 후보가 네트워크로 연결되는 방식
- root와 field의 허용 조합, 업체·기관 root에서도 분야가 필수인지 여부
- 분야 식별자의 분류체계 구분, 계층 선택 시 하위 분야 포함 규칙
- 1차·2차 limit 기본값·최댓값, 2차 limit의 노드별/전체 적용 범위
- 전체 node/edge 상한, 관계별 상위 선정 기준과 안정적인 동점 처리
- 지역 기준과 코드의 허용 조합 및 지표별 필터 적용 의미

관계 전용 읽기 모델과 서버의 일괄 조회·집계·캐시를 사용한다. 기존 집계 규칙을
공유하되 업체마다 프로필이나 경쟁사 Capability를 호출하는 N+1 경로를 만들지 않는다.
nodes·edges·관계 요약을 한 번에 반환하고, 프로필은 노드 선택 후 별도로 조회한다.

노드 쌍당 edge는 하나이며 내부 집계를 다음과 같이 구분한다.

| 관계 | 의미 |
|---|---|
| 계약 | 변경 버전을 병합한 계약사건과 업체 귀속금액 |
| 낙찰 | 참여 기록과 독립적으로 확인되는 낙찰 사건 |
| 관측 참여 | 보존 정책 안에서 확인된 업체의 입찰 참여 |
| 동시 참여 | 두 업체가 같은 공고·차수·분류·재입찰 사건에 참여한 관측 근거 |
| 공동수급 | 원천에서 확인된 공동 계약 당사자 관계 |

동시 참여를 공동수급·협력 관계로 해석하지 않는다. 관계별 사건 집합은 중첩될 수
있으므로 유형별 건수를 더해 전체 사건 수로 표시하지 않는다. 업체 간 edge에 금액을
귀속할 때도 전체 계약금액을 양쪽 업체에 반복 합산하지 않는다. 근거가 없는 귀속은
`null`로 유지한다. 지원하는 관계 유형만 discovery와 응답에서 주장한다.

## 기간·집계 기준과 상세 일치

계약 집계는 최초 계약일을 사용하고 변경 버전 병합, 조회 종료일 이전 최신 금액,
업체 식별 정규화, 공동수급 귀속금액, 최초 계약일 누락 처리를 유지한다. 읽기 모델은
과거 조회 종료일 기준의 버전 선택이 가능해야 하며 최신 상태만으로 과거를 재구성하지 않는다.

공고·참여·낙찰은 각 지표의 명시된 사건일·대체일·중복 제거 단위를 사용한다.
`analysis_basis`에 기간, 시간대, 지표별 날짜 기준, 금액 기준, 집계 정의의 버전을
반환한다. 같은 기간 필터라고 지표별 사건 날짜가 동일한 것으로 해석하지 않는다.

현재 `get_organization_company_relationship`은 공고 연결 사건은 게시일, 공고 미연결
계약은 최초 계약일로 기간을 판단한다. 이 기본 동작을 조용히 바꾸지 않는다.
네트워크 기준의 관계 조회는 명시적 `view_mode=network_edge` 확장으로 계획하고,
모드 생략 시 현재 입력·기간·반환 의미를 보존한다. 모드 이름과 최종 schema는 발행 전
검증한다. 호환 유지가 불가능하면 명시적인 계약 버전 전환과 소비자 이관을 진행한다.

확장 모드는 네트워크와 동일한 필터·관계별 집계 기준으로 기관–업체의 집계와
공고·계약 근거를 페이지 조회한다. 전체 업체·기관 프로필은 포함하지 않는다.

- 네트워크는 읽기 모델의 `snapshot_id` 또는 데이터 버전을 반환한다. 상세와 cursor도
  같은 기준점에 결속한다. 만료된 기준점은 명시적 오류로 처리하고 최신 기준점으로
  조용히 교체하지 않는다.
- 링크 요약은 표시된 근거 페이지가 아니라 해당 두 노드의 필터 적용 후 전체 집계다.
  동일 기준점의 상세 전체 집계와 일치해야 한다.
- 상세 조회의 필터와 기준점이 달라지면 별도 조회로 처리한다. 그래프의 전체 요약과
  화면에 남은 상위 노드·edge의 합계도 구분한다.
- `updated_at`의 읽기 모델 갱신 시각과 원천 수집 기준일을 구분해 반환한다.
- 조건부 업체–업체 상세는 관측 동시 참여 근거만 제공한다. 양쪽의 참여 기록과
  결과가 확인된 사건에서만 승패를 표현하며 경쟁사 목록만으로 승패를 추정하지 않는다.

## 표시 제한·관측 범위·실패

의도적인 상위 N개 제한은 `truncation`, 원천 수집 범위는 `coverage`, 서버 오류나
시간 제한으로 인한 부분 결과는 별도 오류 상태와 이유로 구분한다. 실패로 빠진
결과를 정상적인 상위 결과처럼 반환하지 않는다.

`omitted_node_count`, `omitted_edge_count`는 필터 적용 후 확장 대상에서 표시 제한으로
제외된 고유 수를 뜻한다. 정확한 계산이 불가능하면 `null`과 미산정 여부·이유를
반환한다. 모르는 값은 0으로 반환하지 않는다. 반환 edge는 반환 node만 참조한다.

참여의 현재 보존 범위인 개찰 상위 10위와 원천 응답에 있는 최종 낙찰업체 정책을
새 모델에서도 유지한다. 수집 완료는 전체 참여 이력의 완전성을 뜻하지 않는다.
전체 참여 성공률을 추정하지 않으며 실패·수집 중·확인 불가 상태를 구분한다.

분야 시장의 “전체”는 Runtime의 수집 범위 내 전체다. 표본 여부, 원천별 범위·수집
기준일, 최초 계약일 누락과 금액 산정 불가 범위를 반환한다. 연도별 고유 업체 수를
단순 합산해 전체 업체 수로 제공하지 않는다. 시장 전체 계약금액과 업체별 귀속금액은
집계 단위와 중복 제거 기준을 구분한다.

지역 옵션은 기관 소재지·업체 소재지·수행 지역·참가 지역 제한 등 실제 지원하는
기준만 제공한다. 준비되지 않은 지역·분류 입력은 명시적 검증 오류로 거절하고
무시하거나 추정하지 않는다. 이 입력 검증은 지역 옵션 Capability 출시 전부터 적용한다.

## 성능과 인수

| 대상 | 협의할 P95 목표 |
|---|---|
| 자동완성 | 200ms 이하 |
| 네트워크 응답 캐시 hit | 1초 이하 |
| 네트워크 응답 캐시 miss | 2초 이하 |

cache miss는 준비된 읽기 모델에 대한 조회이며 모델 최초 생성 시간을 포함하지 않는다.
목표를 확정할 때 데이터량, 동시 요청 수, 조회 기간, root·분야·지역, depth,
node/edge 상한, payload 크기, 측정 시작·종료 경계와 반복 표본 수를 함께 정한다.
캐시 TTL·갱신·무효화와 snapshot 보존 기간도 확정한다.

DB 연결 대기·단계별 SQL·직렬화·외부 호출·캐시 조회·전체 처리 시간을 계측하고
hit/miss와 반환 크기를 기록한다. 자동완성·네트워크에서 외부 호출이 없고 노드 수에
비례하는 프로필 호출이 없음을 확인한다. 질의·사업자번호·인증정보는 계측 로그에
그대로 남기지 않는다.

입찰체크가 보고한 단회 확인(2026-10-13, 키워드 `유지관리`)은 2024년부터의
`latest_only` 공고 검색 7.49초, 최근 90일 `all` 검색 0.95초다. 서로 다른 조회 범위와
차수 조건의 관측값이며 이 저장소에서 재측정한 결과가 아니다. 전체 성능이나 P95를
보장하는 벤치마크로 사용하지 않는다.

인수 시 다음을 확인한다.

- 변경계약 최초 연도 귀속, 종료일 이후 버전 제외, 공동수급 귀속, 누락 최초 계약일,
  동일 공고의 복수 계약사건, 업체 식별 정규화가 기존 집계 규칙과 일치한다.
- 같은 필터·기준점의 링크와 상세 전체 집계가 일치하고 페이지 변경에도 요약이 유지된다.
- 동시 참여·공동수급이 분리되고 관측 범위 밖 참여를 완전한 이력으로 표시하지 않는다.
- 미지원 필터, 빈 결과, 표시 제한, 수집 부족, 부분 실패, 취소, 만료 cursor를 구분한다.
- 기존 관계 조회의 모드 생략 호출이 호환되며 제한된 그래프가 dangling edge를 만들지 않는다.
- 정한 부하 조건에서 cache hit/miss와 단계별 지연을 측정한다.

## 구현 순서와 소유권

1. 자동완성과 공식 분류 카탈로그. 지원 필터 검증과 관측 범위 표시는 이 단계부터 적용한다.
2. 네트워크 일괄 조회와 기존 기관–업체 관계 확장. snapshot·상위 제한·근거 일치를 검증한다.
3. 지역 옵션과 분야 시장 집계. 준비된 지역 기준과 수집 범위만 추가한다.

지속적인 검색 인덱스·관계 읽기 모델 생성·갱신과 Data DB migration은 `pipelines/`가
소유한다. 조회·집계·캐시·Capability 계약은 `platform/`의 공공조달 Domain이 소유한다.
MCP가 필요한 경우 Runtime API client와 protocol만 `mcp/`에 둔다.
이 계획 자체로 active Registry·Published artifact·Ontology를 변경하지 않는다.
