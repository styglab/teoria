# Teoria 사용 안내

Teoria에서 하는 일은 **데이터 자산 확인 → 업무 의미 연결 → 변경안 검토 → 업무 앱 활용**이다.
플랫폼의 첫 업무 앱은 규격서 분석이다. 법령 수집은 메타데이터 진단의 근거를 제공한다.

## 시작하기

1. [환경 설정](deployment/configuration.md)에 따라 인증정보와 연결을 준비한다.
2. [Compose](deployment/compose.md)로 필요한 서비스를 실행한다.
3. 기본 주소 `http://localhost:8081/`에서 관리 화면을 열고 관리자 연결을 확인한다.

EC2 환경은 [K3s 안내](deployment/k3s.md)를 따른다. 로컬 검증이 EC2 배포 성공을 뜻하지는 않는다.

## 어떤 화면에서 무엇을 하나

| 메뉴 | 하는 일 |
|---|---|
| 홈 | 검토 대기·실패한 실행·최근 작업 확인 |
| 데이터 자산 | 테이블·컬럼·설명·계보 확인, 자산별 진단 실행 |
| 온톨로지 | 업무 개념·속성·관계 작성, Draft 검토·승인·게시 |
| 의미 연결 | 업무 개념과 OpenMetadata 용어·자산 등의 연결 관리 |
| 검토함 | 변경 제안과 의미 연결·Ontology 검토 대상을 찾아 소유 화면으로 이동 |
| 파이프라인 | 실행·스케줄·취소 요청·이력 확인 |
| 규격서 분석 | 문서 입력, 처리 실행, 물품 구조·속성·원문 근거 확인 |
| 모델 레지스트리·추론 서비스 | 선택형 모델 운영 기능이 켜진 환경에서 모델·배포 버전 관리 |
| 연결 및 설정 | 외부 연결·실행 도구·관리자 인증 확인 |
| 개발 도구 | 실행 계약과 Runtime 개발 기능 확인 |

화면 경로·권한과 상세 사용법은 [Admin UI](platform/admin_ui.md)를 따른다.
검토함과 홈의 건수는 조회 범위의 결과다. 전체 누적 건수나 개인 할당 작업 수로 간주하지 않는다.

## 규격서를 처리하려면

`규격서 분석`에서 원본을 선택하고 처리 방식을 고른다.

| 방식 | 목적 |
|---|---|
| 표준관리 | 원문을 추출하고 표준·의미 후보를 관리 |
| 문서처리 | 지정한 고정 표준/프로파일로 문서를 처리 |

두 방식은 같은 단계를 사용한다.

```text
원본 준비 → 파싱 → 물품·구성·관계 추출 → 요구조건 추출
 → 대상·역할·범위 해석 → 검증·저장 → 사전 연결 → 표준 적용 → 보고서
```

Codex는 공통 흐름의 물품·관계 추출, 요구조건 추출, 대상·역할·범위 해석에 사용한다.
표준관리 모드에서는 미해결 표현의 표준 정의·의미 매핑도 판단하고 재검증한다.
검증을 통과하면 기본적으로 로컬 사전에 자동 승인·반영하며, 제안만 저장하도록 설정할 수도 있다.
사전 조회와 승인 매핑 재사용은 코드와 Admin API가 담당한다.
[단계별 설명·Codex 호출](procurement_specification_processing/pipeline.md)을 참고한다.

기본 **문서 분석 결과**는 `extracted.json`의 검토 전 관찰이다. 문서 속성명·값·단위·조건을
보존하고, 원문 명칭이 없으면 내부 식별자를 표준명처럼 표시하지 않는다.
**표준 매핑 비교**는 같은 실행의 `normalized.json`을 문서 ID·속성 ID로 정확히 연결하여
표준 식별자와 매핑 상태를 별도 열로 표시한다. 조회 실패·결과 없음·기록 없음은 미매핑과 구분하며,
자동 매핑 결과가 사람의 검토·승인을 뜻하지는 않는다.
구성품 트리·속성 표·원문 패널은 각각 스크롤할 수 있다. 속성 행을 클릭하거나 Enter로 선택하면
행과 대응 원문 노드를 함께 강조한다. 좁은 화면에서는 원문 패널을 겹쳐 열고 닫아 속성 목록으로 돌아간다.

결과에서는 다음을 확인한다.

- **물품 구조:** 납품 범위와 구성 관계를 구분한다. 근거가 없는 구성은 확정하지 않는다.
- **속성:** 대상·값·단위·비교 조건·역할·적용 범위를 함께 본다.
- **원문 근거:** 문서 버전과 위치를 확인한다.
- **보류:** 불확실한 관계·의미는 삭제하지 않고 사유와 함께 남긴다.

`partial`은 일부 처리는 저장됐지만 보류·미해결 항목이 있다는 뜻이다.
Prefect의 `Completed`와 문서의 의미 정확도는 다르다.
실행·단계별 로그는 파이프라인 화면에서, 저장된 분석 결과는 규격서 분석 앱에서 확인한다.

## 사전·프로파일·Ontology는 어떻게 다른가

| 구분 | 저장하는 것 |
|---|---|
| 원문 표현 사전 | 규격서에 나온 명칭·소유 대상·근거 |
| 표준 개념 사전 | 공통 정의·자료형·단위·적용 대상과 개정 이력 |
| 의미 매핑 | 원문 표현이 어느 표준 개념에 해당하는지와 승인 상태 |
| 정규화 프로파일 | Published Ontology 개념을 문서에 적용하는 승인된 규칙·고정 패키지 |
| Business Ontology | 여러 시스템에서 유지할 업무 개념·속성·관계의 의미 |

[사전](platform/goods_dictionary.md) · [프로파일](procurement_specification_processing/normalization_profiles.md) ·
[Ontology](platform/ontology.md)에서 각각의 승인 경계를 확인한다.
원문 등록·문서 처리·사전 개정 승인이 Published Ontology 게시를 대신하지 않는다.

## 데이터 자산을 정비하려면

1. 데이터 자산에서 테이블·컬럼과 현재 metadata를 확인한다.
2. 설명 변경안이나 AI 진단을 요청한다.
3. 검토함에서 현재 값·제안·근거를 대조한다.
4. 권한 있는 사용자가 승인하면 적용 서비스가 원천 버전을 다시 확인하고 반영한다.

OpenMetadata가 기술·거버넌스 metadata의 기준이다. Teoria는 제안·검토·적용 이력을 관리한다.
[자산 맥락](platform/metadata/asset_context.md) · [진단](platform/metadata/asset_assessment.md) ·
[승인·적용](platform/metadata/suggestions.md)을 참고한다.

## 결과는 어디에 저장되나

물품 공고 백업은 별도 복원 도구로 선별·검증한다. 공고의 원문 버전·관측·첨부 URL은
Data DB에서 보존하며, 첨부 URL 보유가 다운로드나 규격서 처리를 뜻하지는 않는다.
운영 반영과 실제 복원 결과는 [운영 복원 기록](verification/goods_notice_production_restore_2026_10_28.md),
저장·복원 절차는 [Data DB 안내](pipelines/database.md)를 따른다.

| 위치 | 내용 |
|---|---|
| 파일/S3 | 원본·문서별 추출·표준 적용 결과·보고서 |
| Data DB | 수집 원본·관측, 실행 상태·문서별 요약·산출물 URI와 checksum |
| Application DB | Ontology·Binding·사전·프로파일·제안과 승인 이력 |
| OpenMetadata | 데이터 자산·설명·용어·거버넌스·품질·계보 |

문서 원본·추출 본문을 실행 DB나 OpenMetadata에 중복 적재하지 않는다.
자세한 책임은 [아키텍처](architecture/overview.md), 현재 한계와 다음 작업은 [로드맵](roadmap.md)을 따른다.
