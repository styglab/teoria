# 물품 공고 운영 DB 복원 — 2026-10-28

현재 Compose 운영 `teoria_data`에 migration `101_goods_notice_evidence.sql`을 적용하고,
물품 공고·원문 버전·백업 관측·첨부 참조를 복원해 COMMIT했다.
Data/App 컨테이너·운영 서비스 이미지·Runtime 게시 artifact의 구성은 유지했다.

저장 계약과 코드의 보호 검사는 [격리 복원 검증](goods_notice_restore_validation_2026_10_28.md),
원본 백업의 선별 범위는 [백업 조사](goods_notice_backup_inventory_2026_10_28.md),
첨부 조회 SQL은 [Data DB 안내](../pipelines/database.md)를 따른다.

취소·변경 공고와 이전 차수를 보존했고, 최신 차수만 골라 복원하지 않았다.

`enrichment_checked_at`·`enrichment_claimed_at`은 초기화했다.

## 백업과 실행

- 적용 직전 전체 Data DB를 새 custom dump로 백업했다: **8,101,799 bytes**.
  SHA-256은 `f39059e721851c8c1f3ca6cd564ace161777dc0c41477b2074ca3d2338a7ac88`이다.
  `pg_restore --file=/dev/null`로 전체 내용을 읽는 검사를 통과했다.
- migration·복원 코드·CLI가 격리 검증 자료와 같은 SHA-256임을 확인했다.
- 대상 DB `teoria_data`, 역할 `teoria_pipeline`, 공고 0건, migration 1~100을 확인했다.
  검토한 migration 101만 실행하고 적용 이력을 기록했다.
- 운영 Worker의 Data DB 연결만 사용하는 별도 일회성 프로세스에서 실행했다.
  프로세스는 CPU 1개·메모리 1 GiB로 제한하고 검증된 코드를 읽기 전용으로 연결했다.
  접속정보는 환경변수로만 전달해 파일·로그에 기록하지 않았다.
- 선별 파일의 checksum과 모든 원문 JSON 해시·식별자·건수를 검사한 뒤
  공고·버전·관측·첨부·최신 차수·계보 요약을 하나의 transaction에서 적재했다.
- 기존 공고 트리거 세 개만 transaction 안에서 잠시 중지하고 복구했다. FK는 유지했다.
  공통 ingestion checkpoint·실행·원본·법령·규격서 데이터에는 쓰지 않았다.

복원 배치는 `399468ff-cfd7-5067-b43d-65f405f932f5`다.
적용·복원·보존 비교의 전체 소요 시간은 **1,043.71초**였다.
이는 당시의 CPU·메모리·디스크 조건에서 관찰한 값이며 일반 성능 보증이 아니다.

## 독립 재검증

운영 DB를 read-only transaction으로 다시 읽어 다음을 확인했다.

- 현재 공고와 불변 버전 **각 758,443건**, 합계 **1,516,886건**의 canonical JSON SHA-256과
  원문 식별자를 전수 계산했다. 해시·식별자 불일치는 모두 **0건**이다.
- 원문 버전에서 첨부 튜플 `(공고번호, 차수, 원문 해시, 슬롯, URL, 파일명)`을 재구성하고
  실제 저장된 **1,848,691건**과 비교했다. 튜플별 SHA-256을 정렬해 다시 해시한 값과 건수가 일치했다.
  원문 본문을 반복적으로 join하지 않고 순차 읽기와 제한된 메모리로 검사했다.
- 기존 트리거 세 개가 모두 활성 상태이며 유효하지 않은 인덱스·미검증 제약은 없다.
- 동일 전체 파일의 재실행은 `already_imported=true`를 반환해 중복 적재하지 않았다.
- 최종 Admin·Runtime·법령 검색·활성 artifact도 작업 전과 동일했다.

독립 검증은 **599.61초** 걸렸고, 검증 시 Data DB 크기는 **6,991,599,283 bytes**(약 6.51 GiB)였다.

## 자료와 범위

`backups/teoria/goods_notice_production_restore_20261028T044948Z/`에 새 운영 백업,
manifest·검증한 코드·실행 로그·기존 테이블 전후 해시·서비스 확인 결과를 보존한다.
원본 백업과 선별 파일은 변경하지 않았다. 실제 공고 본문·첨부 URL·인증정보를 Git 문서에 옮기지 않았다.
디렉터리는 0700, 파일은 0600으로 제한하고 `SHA256SUMS`를 검증했다.
복원·검증·재실행용 일회성 컨테이너는 모두 제거됐으며 운영 Data DB 컨테이너 ID와 자원 상한은 유지했다.

수집 기간 전체의 완전성, URL 다운로드 가능 여부, 첨부 파일 내용·규격서 여부는 별도 확인 대상이다.
Provider API 재호출·첨부 다운로드·구형 자동 파싱·참가자격 판단·조달 전체 수집은 실행하지 않았다.
새 수집을 위한 checkpoint를 생성하거나 진전시키지 않았으며 현재 자동 수집도 비활성이다.
후속 작업은 물품 전용 증분·과거 수집 계약과 Flow 검증, 첨부 URL 확인,
명시 선택한 문서의 규격서 처리 연결이다.
