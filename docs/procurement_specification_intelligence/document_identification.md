# 조달 규격서 후보 선별 로직

상태는 **공통 확인 우선순위 구현·서버 문서 최소 검증 완료**다. 이전 식별기와
품목별 예외·단일 문서 보완 규칙은 삭제한 상태로 유지한다. 이후 사용자 요청에 따라
서버 문서 확인 → 최소 파싱 → 공통 우선순위 구현 → 추가 표본 진단을 진행했다.
현재 버전은 `attachment_review_v3`이며 규격 포함 여부를 확정하는 분류기가 아니다.
수집 Flow·API·Registry·운영 배포에는 연결하지 않았다.

서비스 전체는 [전체 설계](overview.md), 개념과 관계는 [도메인 모델](domain_model.md)을
따른다. 아래는 개발용 우선순위 규칙과 후속 설계 제안이다. API·DB 계약이나 실제
규격서 회수율 80% 달성이 확정됐다는 뜻은 아니다.

실행 범위와 원문·파싱 관측은 [서버 검증 기록](computer_server_validation.md)에 정리했다.
이후 kordoc을 고정하고 새 공고 20건·첨부 68개로 수행한 개발·평가 결과는
[선별 적정성 평가](selection_evaluation_2026_10_20.md)를 따른다. 이전 v2 평가 집단의 실제 서버
공고 회수는 8/9, 선정 파일 정밀도는 10/11이었다. 미확인·작은 표본의 한계를 함께 보고한다.

## 현재 로직 요약

현재 로직은 **파일명에 적용하는 결정론적 키워드 규칙**이다. 공고의 물품 규격명
`prdctSpecNm`에서 참조 문구를 받아 근거로 기록하지만, v3 선정에는 사용하지 않는다.
같은 입력과 같은 규칙 버전은 같은 결과를 반환한다. LLM·본문 검색·다운로드·파싱을
선별 함수 안에서 실행하지 않는다. 첫 검증 품목은 컴퓨터서버지만 함수에는 품목 코드를
전달하지 않으며, 품목별 전용 키워드나 예외도 없다.

```text
원본 파일명 + 공고의 규격 참조 문구(prdctSpecNm)
→ 비교용 문자열 정규화
→ 우선순위가 있는 키워드 규칙 적용
→ 우선 확인 / 추가 확인 / 수동 확인 + 사유·근거·버전
```

| 반환값 | 의미 | 기본 선정 정책 |
|---|---|---|
| `first_review` | 직접 규격 표현이 있고 양식·공고·계약 역할 충돌이 없어 먼저 확인 | 후보 선정 |
| `additional_review` | 관련 문서 역할이 있어 별도 검토 가능 | 자동 선정하지 않음 |
| `manual_review` | 이름이 불명확하거나 양식·평가·복합 역할 때문에 자동 선정 보류 | 미선정, 목록은 보존 |

선정은 후속 내용 확인 대상으로 삼는다는 뜻이다. 함수 결과만으로 다운로드를 실행하거나
규격 포함 여부를 확정하지 않는다. 모든 반환값의 내용 상태는 `not_reviewed`다.

### 정밀도 우선 정책과 기존 평가

사용자가 선정 문서로 모델을 만들기 위해 정확성을 요구함에 따라 v3부터 **우선 확인만**
후속 검수 후보로 선정한다. 원천 참조만으로 제안요청서·공고문 등을 우선 확인으로
승격하는 동작도 제거했다. 원천 참조 단서는 보존하지만 자동 선정 근거로 쓰지 않는다.

기존 평가용 공고 10건·첨부 32개를 v3로 다시 계산한 결과 후보 8개에서 규격이
확인됐고 오선정은 0개였다. 그러나 **기존 표본을 재사용한 사후 점검이며 독립 평가가
아니다.** 같은 정책으로 개발 자료에서는 후보 6개 중 4개만 내용 확인이 됐고 2개는
미확인이었다. 따라서 후보 선정 자체를 학습용 정답으로 사용하지 않는다.

| v3 사후 점검 지표 | 기존 평가 자료에서 관측한 결과 |
|---|---|
| 후보 파일 중 요구규격 확인 | 8/8, 100% |
| 실제 서버 규격이 확인된 공고의 회수 | 7/9, 77.8% |
| 내용이 확인된 규격 파일의 회수 | 8/12, 66.7% |

현재는 회수율 80%보다 모델 구축 자료의 신뢰도를 우선한다. 위 100%는 전체 데이터의
정밀도 보장이 아니며, 원문 대조·학습용 승인도 끝났다는 뜻이 아니다.

아래 수치는 이전 v2의 **우선 확인 + 추가 확인** 정책에 대한 독립 표본 관측치이며,
현재 정책의 성능으로 인용하지 않는다.

| 지표 | 관측 결과 | 해석 |
|---|---|---|
| 실제 서버 규격이 확인된 공고의 회수율 | 8/9, **88.9%** | 해당 공고에서 규격 문서를 하나 이상 선정 |
| 선정 파일 정밀도 | 10/11, **90.9%** | 선정 파일 중 실제 요구규격이 확인된 비율 |
| 확인 가능한 규격 파일 회수율 | 10/12, **83.3%** | 내용이 확인된 규격 파일 중 선정한 비율 |
| 미선정·내용 미확인 파일 | 3개 | 실제 규격 포함 여부를 확정하지 못함 |

v2의 관측 지표는 80%를 넘었지만, 미확인 3개를 고려한 문서 회수율 범위는 **66.7~83.3%**다.
따라서 **전체 문서 회수율 또는 품목별 80% 목표 달성은 아직 미검증**이다. 우선 확인만
선정하면 같은 표본의 서버 공고 회수율은 7/9, 77.8%로 낮아진다. 표본·검수 한계와
오류 사례는 [선별 적정성 평가](selection_evaluation_2026_10_20.md)를 따른다.

## 현재 작업 범위: kordoc 고정, 선별 로직 적정성 평가

사용자 지시에 따라 현재 파서는 **kordoc 4.22.15**로 고정한다. 기존 실험과 같은
옵션 `ocr: false`, `images: false`를 유지하고, 원본 hash·파서 버전·옵션을 평가에
기록한다. 지금 판단할 대상은 **파일명 기반 선별이 실제 규격 포함 문서를
잘 찾는가**다. 파서 비교·교체·고도화나 전체 Document JSON 완성을 선행 조건으로
두지 않는다. 파싱 한계는 선별 평가의 미확인 원인으로 별도 기록한다.

### 평가할 선별 경계

현재 함수는 우선 확인·추가 확인·수동 확인을 반환한다. v3 기본 정책은
**우선 확인만** 선정 집합으로 평가한다. 이전 v1·v2 평가를 재현할 때는 당시 정책인
우선 확인 + 추가 확인을 명시한다. 추가·수동 확인 대상은 기본 선정 집합에 포함하지
않지만, 검증 표본에서는 누락을 찾기 위해 함께 읽는다.
두 정책을 뒤섞거나 결과를 본 뒤 유리한 정책으로 합격 기준을 바꾸지 않는다.

### 내용 정답과 선별 결과의 독립

평가 표본의 선정·미선정 첨부를 모두 kordoc으로 파싱하고, 파일명의 선정 결과와
독립된 내용 기준으로 다음 상태와 근거 위치를 기록한다. 후보를 선정했다는 사실이나
기술 키워드의 존재 자체를 내용 정답으로 사용하지 않는다.

| 내용 상태 | 판정 기준 |
|---|---|
| 규격 포함 | 실제 납품 대상의 기술·성능·재질·치수·용량·구성 등 요구규격을 하나 이상 확인 |
| 규격 미관측 | 검토 가능한 본문을 확인했으나 실제 납품 대상의 기술 요구규격을 찾지 못함. 확인 범위를 기록 |
| 미확인 | 다운로드·파싱 실패, 누락 의심, 예시와 실제 요구의 모호함 등으로 판단할 수 없음 |

입찰 제출 절차·평가표·빈 양식·다른 장비의 예시 규격·다른 파일을 보라는 참조만으로는
규격 포함으로 판정하지 않는다. 구성과 사양이 기입된 문서는 반드시 '이상' 같은
연산자가 있어야만 규격 문서가 되는 것은 아니다. 문서의 규격 포함 여부와 **실제
대상 품목이 컴퓨터서버인가**는 별도 항목이다. 코드가 서버여도 상세 내용이 그래픽카드인
사례는 구분해 보고하고 서버 규격 회수 성공으로 자동 집계하지 않는다.

### 비교와 개선

1. 공고 표본·첨부 전체 목록, 선별 규칙 버전과 선정 정책을 고정한다.
2. 선별 결과를 먼저 저장한 뒤 선정·미선정 파일의 파싱 결과를 검수해 내용 정답·대상 품목·근거를 만든다.
3. 규격 포함인데 미선정이면 누락, 선정했지만 규격 미관측이면 오선정으로 분리한다. 미확인은 어느 쪽으로도 확정하지 않는다.
4. 선정 파일 정밀도, 실제 대상 품목의 규격이 있는 공고에 대한 회수율, 다운로드·파싱 비용, 미확인 수와 비율을 함께 보고한다.
5. 내용 근거가 있는 오선정·누락만 사용해 공통 선별 규칙을 수정하고, 별도 고정 평가 표본에서 다시 측정한다.

내용 미확인이 남은 표본은 평가 가능 범위·분모와 제외 수를 공개하고, 미확인 때문에
전체 성능을 판정할 수 없으면 80% 달성 여부도 미확정으로 남긴다. 기존 2개 추가
공고는 진단 사례이며 실제 회수율 80%를 입증한 정답 세트가 아니다.

실제 서버 규격이 이미 확인된 공고에서 선정 집합이 비어 있거나 가능한 회수 문서가
없으면 미선정 이미지가 미확인이어도 확정 누락으로 센다. 완전 검수된 공고만 골라
누락을 숨기지 않는다. 선정한 미확인 문서에 회수 가능성이 남아 있으면 성공·누락을
단정하지 않고 알려진 실제 서버 공고의 회수 범위와 함께 보고한다.

## 1 재검토 결론

첫 검증 품목은 **컴퓨터서버, 원천 세부품명번호 4321150102**다. 검증 대상을 좁히는
것과 처리 흐름을 서버 전용으로 만드는 것은 구분한다. 첨부 후보 식별부터 파싱·품목
구분·구성요소·요구조건·속성 매핑까지의 입출력 구조는 모든 물품에 적용할 수 있게
설계한다. 서버의 CPU·메모리 속성과 검증 사례는 도메인 데이터로 다룬다.

메타데이터로 할 수 있는 일은 **읽을 문서의 우선순위를 정하는 것**이다. 파일명이나
품목 코드만으로 실제 요구규격 포함 여부·대상 품목·공고 전체의 문서 완전성을 확정하지
않는다. 본문 내용의 확인은 원본 직접 검수 또는 파싱·후속 문서 이해의 책임이다.

## 2 기존 접근을 채택하지 않는 이유

- 품목별 코드에 문구 예외를 추가하면 유지보수 대상이 늘고 다품목 문서 귀속을 보장하지 못한다.
- 제목·품목 코드가 있다는 사실만으로 제안요청서 등을 선정해도 요구규격이 있다는 증거는 아니다.
- 사양서를 참조하면서 첨부가 하나뿐이라는 사실로 그 문서에 사양이 있다고 추정할 수 없다.
- 후보가 있는 공고 비율을 올려도 실제 규격서 정밀도·회수율이 개선됐는지는 알 수 없다.

과거 수치와 자료는 [폐기한 메타데이터 실험 기록](evaluation_2026_10_20.md)에 남기되
현재 성능이나 새 설계의 검증 결과로 사용하지 않는다.

## 3 판단 대상과 책임

| 질문 | 판단 시점 | 근거 |
|---|---|---|
| 어느 첨부부터 확인할 것인가 | 메타데이터 선별 | 원본 파일명·원천 참조·전체 첨부 목록 |
| 파일을 가져와 처리할 수 있는가 | 다운로드·형식 검사 | URL·응답·실제 형식·손상·암호화·처리 예산 |
| 문서에 요구규격이 있는가 | 원본 검수 또는 파싱 후 문서 이해 | 실제 기술·성능·재질·치수 등의 요구조건과 위치 |
| 어느 품목의 규격인가 | 문서 이해 | 품목 경계·표·문단·공고 품목 목록의 연결 |
| 어떤 속성과 조건인가 | 요구조건 추출·속성 매핑 | 원문 조건·논리·단위·속성 의미 |

우선순위와 내용 판정을 같은 상태로 저장하지 않는다. 미확인 문서를 비규격 문서로
간주하지 않으며, 내용 확인 실패도 규격 없음으로 처리하지 않는다.

## 4 공통 입력과 근거 보존 제안

- 공고번호·차수·첨부 식별자 또는 원천 슬롯과 원본 파일명·URL을 보존한다.
- 같은 원천 슬롯의 ntceSpecFileNmN과 ntceSpecDocUrlN을 연결한다. 슬롯 번호로 URL을 재구성하지 않는다.
- 공고 제목·품목 코드 목록은 대상 표본과 문서 이해의 문맥이다. 개별 파일을 특정 품목에 자동 귀속하지 않는다.
- prdctSpecNm 같은 원천 참조 표현은 원문과 함께 기록한다. 공식 첨부 역할 코드라고 가정하지 않는다.
- 같은 공고의 첨부 목록은 확인 대상의 누락·복합문서 가능성을 살피는 문맥으로 사용한다.
- 동일 파일명의 HWP/PDF를 내용 확인 전 중복으로 삭제하지 않는다.

정규화는 원본과 분리하며 NFKC·case folding과 공백·구분자 제거로 표기 차이를
비교한다. 현재 키워드·우선순위는 아래 개발 규칙으로 기록하고 변경 시 버전을 바꾼다.

### 나라장터 문서구분값의 현재 수집 상태

2026-10-20에 DB에 저장된 2026년 물품공고의 `source_payload` 필드명과 현재
입찰공고정보서비스 Connector 계약·보관된 공식 참고문서 1.2를 확인했다.

| 원천 항목 | 현재 상태 | 선별에서의 의미 |
|---|---|---|
| `ntceSpecFileNm1`~`ntceSpecFileNm10` | 수집 원문에 있음 | 파일명 규칙의 입력 |
| `ntceSpecDocUrl1`~`ntceSpecDocUrl10` | 수집 원문에 있음 | 같은 슬롯의 파일 다운로드 주소 |
| `stdNtceDocUrl` | 수집 원문에 있음 | 표준공고서 URL이며 첨부별 문서구분값이 아님 |
| `prdctSpecNm` | 수집 원문에 있음 | 규격 설명·참조 문구, 공식 첨부 역할 코드는 아님 |
| 첨부별 문서구분 코드·명칭 | 현재 수집 데이터·확인한 계약에서 확인되지 않음 | 현재 규칙에서 사용하지 않음 |

`ntceSpecDocUrlN`의 명칭은 공고규격서URL이지만, 실제로 공고문·서식 등도 포함한다.
이 필드에 들어 있다는 사실만으로 규격서로 판정하지 않는다. 다운로드 URL의
`fileType`·`fileSeq`도 문서구분의 공식 코드 의미가 확인되지 않았으므로 판단에 사용하지 않는다.

나라장터 화면의 문서구분값을 별도 조회로 확보할 수 있는지는 미확인이다. 현재 데이터에
없다는 사실을 나라장터 전체에서 제공하지 않는다는 뜻으로 해석하지 않는다. 확보되면
필드·코드 의미와 첨부 연결을 검증한 뒤 **원천 문서구분 우선 → 누락·불명확 시 기존
메타데이터 규칙 → 파싱 후 내용 확인** 순서의 다음 버전을 검토한다. 이 경로는 현재
구현하지 않았으며 문서구분값 자체도 실제 요구규격 포함의 최종 정답으로 사용하지 않는다.

### 공통 확인 우선순위 규칙

아래 순서를 위에서부터 적용하고 **처음 일치한 규칙으로 결과를 결정**한다.
따라서 원천 참조가 있어도 양식·평가·안내 단서가 있으면 먼저 수동 확인으로 보류한다.

| 순서 | 조건 | 결과 |
|---:|---|---|
| 1 | 파일명 누락·잘못된 타입 | 수동 확인 |
| 2 | 양식·평가·안내 단서가 있음 | 수동 확인. 다른 단서가 있어도 승격하지 않음 |
| 3 | 직접 규격 표현이 있고 공고·계약 역할 충돌이 없음 | 우선 확인, 기본 후보 선정 |
| 4 | 직접 규격 표현과 공고·계약 역할이 섞임 | 수동 확인 |
| 5 | 관련 문서 역할이 있고 공고·계약 역할 충돌이 없음 | 추가 확인, 기본 후보 미선정 |
| 6 | 나머지 | 수동 확인 |

직접 표현: `규격서`, `사양서`, `시방서`, `구매규격`.

관련 문서: `현품설명서`, `제안요청서`, `과업지시서`, `물품내역서`, `구매내역서`,
`품목명세서`, `물품명세서`.

v2에서는 개발용 원문 근거로 `규격비교조사표`, `산출내역서`, `용도설명서`,
`인프라구성도`를 추가 확인 역할에 더했다. v1을 버전 지정으로 재현할 수 있으며
평가용 내용 검수 전에 v2를 동결했다. 평가용 오류를 이용해 v2를 재수정하지 않았다.

양식·평가·안내: `양식`, `서식`, `평가기준`, `평가항목`, `평가표`, `평가서`,
`작성안내`, `제출안내`, `제출서류`, `검토확인서`, `작성요령`, `제출요령`,
`샘플`, `견본`, `예시`.

공고·계약 역할: `입찰공고`, `공고문`, `공고서`, `계약조건`, `계약특수조건`.

v1·v2에서 사용한 원천 참조 규칙은 다음과 같으며 **v3에서는 근거 기록에만 사용한다.**
원천 참조는 공고문/공고서·특수조건·현품설명서·제안요청서·과업지시서·내역서 중
역할 표현과 `참조`·`참고`·`따름`·`의함`·`첨부`·`별첨`·`붙임`이 함께 있어야 한다.
파일명에서도 해당 역할이 확인돼야 하며 `해당없`·`참조하지`·`참고하지`·`미첨부`·
`미제공`·`별도제공`·`추후제공`이 있으면 참조에 따른 승격을 하지 않는다.

원천 참조와 파일명은 문서 ID의 정확한 연결이 아니라 아래 문구의 부분 문자열 일치로
비교한다. 같은 역할의 파일이 여러 개이면 각각 일치할 수 있으며 문장별 부정 범위까지
해석하지 않는다. 부정 문구가 참조 입력 전체에 하나라도 있으면 참조 승격을 보류한다.

| 참조 문구의 역할 | 파일명에서 찾는 표현 |
|---|---|
| 공고문 또는 공고서 | 공고문·공고서·입찰공고 |
| 특수조건 | 특수조건 |
| 현품설명서 | 현품설명서 |
| 제안요청서 | 제안요청서 |
| 과업지시서 | 과업지시서 |
| 내역서 | 내역서 |

v1·v2에서 참조 승격이 보류되어도 나머지 직접·관련 문서 규칙은 계속 적용한다.
예를 들어 `제안요청서 미제공`이라는 참조 문구만으로 해당 파일을 영구 제외하지 않는다.

결과는 원본·비교용 파일명, 원천 참조, 우선순위, 사유, 일치·충돌 단서와 버전을
보존한다. 모든 결과의 `content_state`는 `not_reviewed`다. 실제 내용 검수 결과는
별도 기록한다. 공고 제목·품목 코드·첨부가 하나뿐이라는 사실은 승격 조건이 아니다.

### 적용 예시와 알려진 한계

| 파일명 | 원천 참조 문구 | 결과 | 결정 근거 |
|---|---|---|---|
| 서버 구매 규격서.hwpx | 없음 | 우선 확인 | 직접 규격 표현 |
| 제안요청서.hwp | 없음 | 추가 확인 | 관련 문서 역할 |
| 제안요청서.hwp | 제안요청서 참조 | 추가 확인 | 참조는 기록하지만 자동 승격하지 않음 |
| 규격서 작성양식.hwp | 없음 | 수동 확인 | 양식 단서가 직접 표현보다 우선 |
| 공고문 및 규격서.hwp | 없음 | 수동 확인 | 공고·규격 역할 혼합 |
| 공고문.hwp | 공고문 참조 | 수동 확인 | 참조만으로 자동 선정하지 않음 |
| 구매대상.pdf | 없음 | 수동 확인 | 일치하는 문서 역할 없음 |
| 평가기준서.hwp | 없음 | 수동 확인 | 평가 단서 |

표현이 일치하면 확장자·실제 지원 형식과 무관하게 우선순위를 부여한다. 파일 형식
검사는 후속 책임이다. 일반 파일명·평가 문서에도 실제 규격이 있을 수 있고,
제안요청서가 제출 절차와 빈 양식만 담을 수도 있다. 실제 평가에서도 이 원인으로
누락·오선정이 관측됐다. 수동 확인은 비규격 판정이나 삭제를 의미하지 않는다.

### 규칙 변경과 검증

현재 기준 버전은 `attachment_review_v3`다. 공통 키워드의 추가·수정·우선순위 변경은
실제 내용 근거를 남기고 새 버전으로 관리한다. v1·v2는 버전을 명시해 재현할 수 있다.
새 규칙은 개발 자료에서 작성하고, 선정·미선정 첨부를 포함한 별도 평가 표본에서
정밀도·공고 회수율·문서 회수율·미확인 비율을 다시 계산한다. 키워드 추가로 후보 수가
늘었다는 이유만으로 개선이나 80% 달성을 선언하지 않는다.

### 모델 구축용 원문 검수와 학습에 사용할 경우의 기준

모델 구축에 사용할 문서는 **후보 선정과 별도로 원문 근거 확인·검수 승인을 마쳐야 한다.**
모델이 Ontology·도메인 모델인지 AI 학습 모델인지는 아직 확정하지 않았다. 전자는
원문에서 발견한 품목·구성요소·속성·조건의 의미 검증이 필요하고, 후자는 아래와 같은
명시적인 정답 라벨과 데이터 분리가 추가로 필요하다.
현재 분류 단위는 첨부파일이며, 양성의 의미는 문서 제목이 규격서라는 것이 아니라
**실제 발주 대상의 요구규격을 포함하는 문서**다. 모델의 구체적인 학습 과제와 출력
단위가 정해지면 그 목적에 맞는 라벨 계약을 별도로 확정한다.

| 단계 | 기준 | 학습 데이터 사용 |
|---|---|---|
| 후보 | 메타데이터 규칙의 우선 확인 | 불가 |
| 내용 확인 | kordoc 본문에서 실제 발주 대상의 성능·용량·치수·구성·호환 등 요구조건과 근거 위치 확인 | 검수 대기 |
| 양성 승인 | 원본 대조로 실제 요구조건임을 확인하고 검수자·승인 기록 보존 | 해당 문서의 양성 라벨 사용 가능 |
| 보류 | 암호화·파싱 실패·이미지 영역·원문 누락 의심·예시와 요구의 모호함 | 제외·별도 검수 |
| 음성 승인 | 충분히 검토 가능한 원문 전체에서 요구규격이 없음을 확인하고 검수 승인 | 해당 문서의 음성 라벨 사용 가능 |

공고번호·차수·첨부 식별자·원본 SHA-256, 파서 버전·옵션, 라벨 정의 버전, 내용 근거와
위치, 검수·승인 이력을 함께 보존한다. 미선정 파일을 자동 음성으로 만들지 않는다.
기존 assistant 단일 내용 검수는 진단용이며, 위 학습용 원문 대조·승인 완료로 간주하지 않는다.
선별 함수의 `content_state`는 승인 후 상태로 변경되지 않으며, 승인 결과는 별도 관리한다.

학습·평가 데이터는 같은 공고의 첨부·변경 차수와 동일·유사 문서가 양쪽에 섞이지 않도록
묶어서 분리한다. 실제 학습용 데이터셋 생성·승인 워크플로와 모델 학습은 아직 구현하지 않았다.

## 5 메타데이터 선별 대안과 권장안

| 대안 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 모든 첨부를 확보·본문 분류 | 내용 근거를 확보할 수 있음 | 운영 비용이 큼 | 초기 기본 방식으로 채택하지 않음 |
| 파일명만으로 규격서 확정 | 저비용·재현 가능 | 본문 포함 여부와 품목 귀속을 알 수 없음 | 채택하지 않음 |
| 메타데이터로 확인 우선순위를 정하고 예산 안에서 본문 검증 | 저비용 선별과 내용 근거를 분리 가능 | 파싱·표본 검수가 필요 | 권장 검토안 |

권장안은 다음과 같은 근거의 강도를 구분한다. 위 공통 함수는 확인 우선순위만
구현하며, 실제 내용 판정이나 자동 다운로드의 허용을 뜻하지 않는다.

| 근거 | 우선순위 검토 방향 | 제한 |
|---|---|---|
| 파일명에 요구규격 문서 역할이 명확함 | 먼저 확인 | 작성양식·평가문서와의 충돌을 확인해야 함 |
| 원천이 지칭한 문서 역할과 실제 첨부가 일치 | 근거만 기록 | v3에서 참조에 따른 자동 승격은 하지 않음 |
| 제안요청서·현품설명서·내역서 등 관련 문서 | 별도 검토 대상으로 보존 | 기본 선정에 포함하지 않음 |
| 양식·평가·공고 등 역할이 충돌하거나 이름이 불명 | 불확실한 대상으로 보존 | 공고문에도 규격이 들어갈 수 있으므로 영구 제외하지 않음 |
| 첨부가 하나뿐이거나 다른 문서가 없음 | 누락·검수 필요성을 기록 | 그 문서를 자동으로 규격서로 승격하지 않음 |

공고에 어떤 역할의 첨부가 누락됐는지와 파일 내용이 무엇인지는 다른 문제다.
특정 공고에서 후보가 없으면 사람 검토·선별 범위 확대 여부를 결정할 수 있지만,
자동으로 남은 파일을 모두 규격서로 처리하지 않는다.

## 6 컴퓨터서버로 검증할 순서

1. 원천 코드 4321150102, 2026년, 최신 차수·취소 처리 기준을 고정해 서버 공고 표본을 정한다.
2. 기존에 내려받은 서버 문서 5개의 원본·메타데이터를 우선 자료로 활용한다. 이 5개는 명확한 파일명으로 선정된 편향 표본이며 식별 성능 평가용 정답 세트는 아니다.
3. 파일명과 원천 참조만으로 알 수 있는 사실, 실제 문서에서만 확인할 사실을 나눠 기록한다.
4. 현재는 kordoc을 고정해 평가 표본을 파싱한다. 파싱 실패·누락 의심은 내용 미확인으로 구분하며 파서 고도화로 작업 범위를 넓히지 않는다.
5. 선정·미선정 첨부를 함께 검수해 실제 규격 포함 여부·대상 품목·근거 위치를 라벨링한다.
6. 그 근거로 공통 선별 규칙을 작성하고 독립 표본에서 평가한다. 검증 전에는 품목별 예외를 추가하지 않는다.

단독 서버 문서를 첫 사례로 쓰더라도 공통 모델에는 여러 LineItem·공통 조건·다수
첨부를 표현한다. 후속 서버 다품목 사례와 두 번째 물품에서 같은 계약이 작동하는지
확인한다. 두 번째 검증 품목은 아직 확정하지 않는다.

## 7 평가와 자원 정책

현재 합격 방향은 **Precision(정밀도) 우선**이다. 후보 선정은 내용 확인과 별개이며,
선정 파일 중 실제 발주 요구규격이 있는 비율을 검수 가능한 근거로 평가한다.
내용 미확인을 임의로 양성이나 음성으로 처리하지 않고 수와 영향을 함께 보고한다.
Recall(재현율)은 참고 지표로 남기며 기존 80% 재현율 목표를 현재 합격 기준으로
적용하지 않는다. 정밀도의 수치 기준과 검증 표본 규모는 아직 확정하지 않았다.

- 메타데이터 단계: 후보/우선 확인 대상의 공고별 비율, 첨부 수, 미확인 사유와 예상 처리량을 보고한다.
- 내용 단계: 실제 규격 포함 여부·대상 품목의 정답을 확보한 경우에만 정밀도와 회수율을 계산한다.
- 이전 회수율 목표 80%는 실제 해당 품목의 규격 첨부가 있는 공고에서 이를 하나 이상 발견한 비율이었다. 현재는 참고 지표이며 모든 요구조건의 완전한 회수를 뜻하지 않는다.
- 정밀도 90%는 이전 제안값으로 남기며, 표본 수·검수 범위·허용 비용과 함께 검토해 확정한다.
- 표본의 미선정 첨부까지 확인해야 누락을 평가할 수 있다. 선정 문서만 검수한 결과로 회수율을 주장하지 않는다.
- 파서 결과의 텍스트 누락이 있으면 미확인으로 보존한다. 필요한 경우 원본을 직접 확인한다.
- 메타데이터 선별은 네트워크·다운로드·파싱·LLM 호출 없이 설계한다. 본문 점검은 별도 파일 수·용량·동시 실행 예산을 적용한다.

파싱으로 텍스트가 추출됐다는 사실만으로 규격 포함 판정이 완료되는 것은 아니다.
후속 문서 이해 또는 사람 검수로 근거 위치와 내용 유형을 확인한다.

## 8 선별 평가를 위해 확정할 사항

- 서버 평가 표본과 선정·미선정 첨부의 검수 범위
- 요구규격을 포함한 문서의 정의와 품목 귀속 기준
- 우선 확인·추가 확인·미확인의 결과 계약과 충돌 처리
- 본문 확인 예산, 실패·보류·재처리 정책
- 정답 구축과 독립 평가 방식, 예외 규칙을 허용할 근거

전체 파서·문서 이해·독립 품질 평가의 상세 계약과 DB migration은 아직 구현하지 않았다.
전체 파서나 공통 Document JSON 구현은 현재 선별 평가의 선행 조건이 아니다.
수집·다운로드·파싱은 Pipelines, 의미·속성·사용자 검색·비교는 Platform의 공공조달
기능에 두며 미래 재사용을 예상한 공통 패키지를 만들지 않는다.

## 9 구현 범위와 남은 평가

현재 메타데이터 우선순위 함수와 기본 후보 선정 정책 `SELECTED_REVIEW_PRIORITIES`는
[`attachment_selection.py`](../../pipelines/src/teoria_pipelines/domains/public_procurement/specification_intelligence/attachment_selection.py)에 있다.
서버 코드를 받지 않으며 네트워크·파서·LLM 호출이 없다. 파서 검증과 제한 다운로드는
`.artifacts/procurement_specifications/server_validation/`의 별도 실험으로 수행했다.
파싱 모듈 전체·공통 Document JSON 변환기·상용 실행 Flow가 완성된 것은 아니다.

기존 20개 서버 공고는 개발 자료로 사용했고, 별도 무작위 공고 2개는 우선순위 규칙을
작성한 뒤 고정해 추가 진단했다. 2개 표본과 관측 기록은 정밀도·회수율을 보고할
독립 정답 세트가 아니다. 특히 코드와 실제 발주 물품이 다른 사례를 구분해야 한다.
이후 20개 공고를 개발 10개·평가 10개로 고정해 내용 기준 선별 평가를 실행했다.
내용 미확인과 품목 불일치를 별도 집계하고 정밀도·회수율·선정 파일 수·bytes를
비교했다. 관측된 공고 회수율이 목표를 넘었다는 것과 모집단 80%를 보장하는 것은
다르며, 문서 단위 회수율에는 미확인으로 인한 불확실성이 남아 있다.

평가 계산은
[`selection_evaluation.py`](../../pipelines/src/teoria_pipelines/domains/public_procurement/specification_intelligence/selection_evaluation.py)에
있다. 내용 라벨을 파일명 규칙으로 생성하지 않으며 오선정·누락·미확인과 대상 품목
관측을 분리한다. 고정한 라벨과 선별 결과로 계산하며 운영 다운로드나 파서 실행을 연결하지 않는다.
